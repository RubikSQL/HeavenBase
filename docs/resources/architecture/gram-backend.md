# Sparse GRAM Strategy Architecture

## Status

Sparse GRAM keyword indexing is a SQL-hosted `SparseGramIndex` strategy adapter. It covers typed `Array[ShortText]` storage routing, strategy-owned analyzer options, native `contained_in` execution on SQL backends through the `sql_sparse_gram` adapter, scan fallback metadata, SQL-owned postings tables, configurable normalization/tokenizer/hash/salt seams, and reserved `match` result metadata.

There is no standalone sparse-GRAM provider. SQL backends own database connections, transactions, dialect behavior, and canonical row storage. The sparse-GRAM adapter uses that SQL backend to maintain index tables beside the canonical entity tables.

## Current Shape

Sparse GRAM supports reverse containment search: stored short `Array[ShortText]` keywords matching long query text. It composes typed storage routing, a parameterized `SparseGramIndex` strategy, configurable normalization/tokenizer/hash/salt seams, SQL adapter-owned keyword/posting tables, and optional `match` result metadata without changing the central router.

## Boundaries

- Storage profiles route `Array[ShortText]` to `SparseGramIndex` on SQL when a SQL backend is available, then fall back to ordinary row storage with scan fallback.
- `SparseGramIndex(...)` is an immutable strategy value. It owns analyzer/index semantics such as `normalizer`, `gram_unit`, `tokenizer`, `gram_width`, and sparse policy options, but it must not hold provider clients, mutate state, perform IO, or compile queries.
- `backends/sql/handler/base.py` compiles SQL-hosted `contained_in` into `QueryFragment` objects with `handler_kind == "sql_sparse_gram_contained_in"` and `strategy_adapter == "sql_sparse_gram"`.
- `backends/sql/strategies/sparse_gram.py` owns SQL-specific adapter lifecycle, index-table DDL/writes, native fragment execution, candidate verification, row hydration from canonical SQL storage, and result-frame construction.
- `backends/sql/strategies/gram/` owns backend-neutral sparse-GRAM analyzer, matching, hash, and runtime contracts used by the SQL adapter.
- The SQL adapter reaches physical storage only through its owning SQL backend's active `Database` object. It does not create its own database connection, provider, local path, retry policy, or canonical row backend.

## Query Metadata

Search metadata uses a reserved query-output column named `match`. This is intentionally public and short, matching the existing query-output style of `score`. The column is not part of an entity schema, but result projection preserves it when selected, for example `.select("target_id", "match")`. Native SQL sparse-GRAM and scan fallback `contained_in` use the same metadata shape; span-capable long-text `contains`/`match` paths can adopt it later without changing the reserved column contract.

`match` is evidence-preserving, not longest-match-only. Candidate lookup deduplicates repeated postings for the same indexed keyword id before exact verification, but every verified stored keyword occurrence is emitted. If one row stores overlapping or containing keywords such as `redis`, `redis query`, and `query engine`, a query containing `Redis Query Engine` returns separate match entries for each keyword. If the same keyword string appears more than once in an array at different ordinals, each ordinal can return its own evidence.

The frame merge rule is generic: a backend or handler marks any reserved result metadata column on the `ResultFrame`, and logical `and` / `or` result merging deduplicates rows by `object_id` while concatenating list values for those metadata columns. `match` is sparse-GRAM-owned metadata, not a central-router special case. `not` returns the remaining rows without evidence from the negated branch.

## Sparse Policy

The optimized default follows the Cursor/AgentHeaven sparse n-gram shape: normalized text is weighted by character trigrams, adjacent trigrams are merged into deterministic sparse spans, and the query string generates a monotonic-stack covering set. The sparse index is only a candidate generator; the SQL adapter exact-verifies `keyword_norm in query_norm` before returning a row.

Normalization and gram generation are separate seams configured through `strategy=hb.SparseGramIndex(normalizer="default", gram_unit="char")`; these are sparse-GRAM strategy options, not generic `.store(...)` options and not physical backend options. The default `normalizer="default"` applies language-neutral Unicode/casefold normalization with punctuation/whitespace collapsing. Opt into `normalizer="auto"` to try spaCy for English-like text when the configured model is available, with fallback to dependency-free normalization for CJK, non-natural-language strings, or missing spaCy. Built-in normalizers include `default`/`simple` for Unicode/casefold plus punctuation/whitespace collapsing, `fast` for the same visible text without origin tracking, `char` for space-separated source characters, and `none` for raw text. Built-in analyzer modes include character grams and token-level grams over registered tokenizers such as `space`. Domain-specific tokenization, such as gene-aware segmentation or whole-word token grams, should be registered with `hb.ext.register_gram_tokenizer(...)` and then referenced by registered identifier; direct callables are only for live Python use and should not be persisted in manifests.

- `gram_width: 3`
- `sparse_max_width: 0`
- `sparse_grams_per_keyword: 0`
- `hot_gram_threshold: 0`

`gram_width` is the base character n-gram width, and the default is always trigrams. `sparse_max_width: 0` keeps generated sparse spans unbounded; a positive value caps which generated spans are preserved as postings, but exact verification remains mandatory. `sparse_grams_per_keyword` is the maximum number of sparse spans stored per keyword; `0` preserves every generated sparse span and is the default. The SQL store checks complete coverage with `COUNT(DISTINCT mask_bit) = part_count`, so it does not materialize every matching posting row in Python.

One- and two-character grams support exact short keywords. Exact three-character keywords use ordinary trigrams. The SQL adapter stores `keyword_len` in its private keyword table and reads all short widths present for the field with one `SELECT DISTINCT` per indexed lookup. An index on keyword length serves that read; HeavenBase 0.1.2.2 made the keyword table without it, and opening such storage adds it. Where the server refuses, such as for a login without that right, lookups read without it. A keyword table in a DuckDB file that has held rows does not get it either, and lookups there read without it: DuckDB cannot write a table again in a later process after a column that no index of it covered was indexed. This lets it generate short-keyword lookup hashes only for widths present in the index, including widths added by another backend instance or process.

`hot_gram_threshold: 0` means no hot-list dropping. Threshold pruning remains disabled by default because it needs corpus-level validation; exact verification protects correctness from collisions, but dropping hot grams can change recall unless the store maintains an explicit residual path.

## Hash And Salt

Sparse-GRAM hash config must include `hash_function`, `hash_bits`, `hash_salt`, and `seed`. CRC32 is the default sparse-gram hash because it is cheap and deterministic; exact verification protects correctness when collisions widen the candidate set. Sparse-GRAM `hash_function` config resolves only built-in `md5`, `sha256`, `crc32`, and optional `xxhash64` / `xxhash128` names; dotted deployment-local hash callables remain available through the generic `heavenbase.utils.resolve_hash_int` utility, but are intentionally not accepted in persisted sparse-GRAM strategy config. `hash_salt` domain-separates sparse-gram weights from other HeavenBase hash utilities and gives future sparse-GRAM versions an explicit rebuild knob. `seed` remains available for deterministic sparse-selection tie-breaking. Changing the hash function, bit width, salt, seed, sparse policy, or normalizer identity makes existing index rows stale and must trigger reindex behavior rather than silent mixed semantics.

## Adapter-Owned Index Storage

SQL sparse-GRAM stores keyword metadata and postings in SQL. The adapter takes candidate IDs from the index and reads their current rows separately. It checks each returned row against the whole filter tree and builds match metadata from that row's keywords. Negations reuse the candidate rows they scanned. Exact verification and SQL near scans apply the configured normalizer and require every reported span to cover whole query units for token- and space-based grams. A hash collision can add candidates, but an embedded partial token does not become a match. The tokenizer sees the full normalized query when verification locates its units. Custom tokenizers return unit values without offsets. When those values align to literal text, a substring must cover the same units at both extremes of the possible alignments. Otherwise, tokenizing the query up to each end of the span must isolate the keyword units, and removing the span from the full query must leave the surrounding units intact. A concurrent write that adds a match after candidate selection can still be missed.

Workspaces that resolve the same sparse-GRAM storage tables share one index per entity field. PostgreSQL routes can use separate indexes in different schemas of the same database. The index fingerprint records the field's sparse-GRAM options and the Context defaults used to build it. The adapter checks that fingerprint before and after each indexed lookup and validates strategy-maintained mutations in the row write transaction. It also refuses a mutation through an entity registration that lacks a binding for a currently indexed field, including an index created after the writer registered, on every SQL route that installs the adapter, also one that keeps no keyword index; on an `oracle` engine at `SERIALIZABLE` a write whose transaction began before another workspace started indexing the entity is not refused, and on a `mysql` engine at `READ COMMITTED` a write that meets the first index of its entity in the window described below is not. A pure delete through a bound adapter can remove postings without using the old field options. Lookups read all indexed short keyword widths in one statement. Combined and exact SQL near scans generate short-width hashes from their own field configuration, so the filter keeps working when a peer rebuilds or retires the shared index.

Rebuilding deletes the old keyword rows before scanning stored entity rows. A registration that changes an entity's stored fingerprints (a new index, a rebuild with other options, a retirement), and only such a registration, first waits for the entity's row writes in progress and holds off new ones until it commits: on the `postgres`, `pgvector` and `oracle` backend types it takes a `SHARE` lock on the entity table; on the `mysql` type it takes shared locks on every row of the entity table and the gaps between them, and reads the index metadata before that with locking reads, because a MySQL transaction reads every row as of its first plain read; on `sqlite` the database's write lock does the same on its own. DuckDB has no lock statement, and a DuckDB file is open for writing in one process at a time, so on `duckdb` a gate in the process does it: a write takes the entity's gate before its row statements, and a registration takes it before the first statement of its transaction and lets it go as soon as it finds no fingerprint to change. A DuckDB transaction reads from a snapshot taken at its first read, so the gate refuses, with `SparseGramIndexConflictError`, a transaction that ran any statement before it took the gate, even one that reads no table, when the other side has changed the entity since; roll that transaction back and try again. The same transaction gives the entity a new epoch in the metadata table. A row write therefore either commits before the registration counts and reads the stored rows, which it then indexes with the new options, or starts after it and sees the new epoch. That holds at every isolation level of the write, with the exceptions named below. On PostgreSQL the registering engine has to run at `READ COMMITTED`, PostgreSQL's default: a registration at `REPEATABLE READ` or `SERIALIZABLE` scans the stored rows in a snapshot taken at its first read, before it waited, so the index it builds misses a row that a write commits after that read, until the row is written again or the index is rebuilt. Register entities through an engine at `READ COMMITTED`, or pause writers while index options change. A transaction at `REPEATABLE READ` or `SERIALIZABLE` reads one snapshot throughout, so a write in it that began reading before the registration committed cannot see the change in that snapshot; it fails instead, and the transaction should be rolled back and run again. On PostgreSQL the write's condition reads the epoch row `FOR SHARE`, so the row statement fails with the database's own serialization failure (`DatabaseError`, SQLSTATE 40001) when the epoch changed after the snapshot, as it does when another transaction wrote the same row since, and so does a locking read of the metadata. For this a registration on PostgreSQL gives every entity of a database that holds the index tables an epoch row; a write that finds index tables its snapshot lacks is refused with `SparseGramIndexConflictError`. `FOR SHARE` takes the `UPDATE` right on `hb_gram_meta`. HeavenBase asks once per backend connection, when it registers the first entity, whether the login may update the `value` column. For a login that may not, the check reads plainly: the check still holds at `READ COMMITTED`, but a write in a `REPEATABLE READ` or `SERIALIZABLE` transaction that began reading before the registration committed is not refused. Such a login can register entities and build, rebuild and retire their indexes; its registrations read the metadata plainly. On MySQL-protocol servers a registration needs no `UPDATE` right on `hb_gram_meta` either. Except on MySQL, lookups, audits and registrations that change no index read the metadata plainly, so a keyword query runs in a read-only transaction. On MySQL the condition and, inside a transaction, the index-metadata reads are locking reads, which see the latest committed rows; at `READ COMMITTED` such a read holds no lock on an epoch row that does not exist yet, so a write at `READ COMMITTED` that reaches the server after a registration that first indexes the entity locked its rows, and before that registration stored the entity's first epoch, is not refused, and its row is missing from that index; `information_schema` shows a `REPEATABLE READ` transaction its snapshot, so a write in a transaction that was already open when the write began reads the index tables once, and is refused with `SparseGramIndexConflictError` when MySQL reports them created after the snapshot. A deadlock between writers (error 1213) is a `DatabaseError`. Oracle has no shared row lock. At its default `READ COMMITTED` each statement reads as of its own start, after the `SHARE` lock it waited for. At `SERIALIZABLE`, such a write fails (`DatabaseError`, ORA-08177) only when it writes keyword rows that the registration rebuilt; a write of an entity that another workspace started to index after the write's transaction began is not refused, and its rows are missing from that index. Write at `READ COMMITTED` on Oracle while indexes change. An Oracle engine set to `SERIALIZABLE` also fails its own keyword-index registrations with ORA-08177. PostgreSQL serializes index registrations for the same entity and metadata table through a transaction-level advisory lock. Routes that register fields in the same PostgreSQL index share one publication transaction, which runs on one route's connection, so registering `SparseGramIndex` fields through routes whose login role, current role or search path differ while they resolve the same index tables raises `ValueError`. PostgreSQL routes whose entity table is one table write each row together through one route whatever their roles; if they resolve different index tables and either binds a `SparseGramIndex` field of the entity, the registration raises `ValueError` too. Routes on one SQLite or DuckDB file, routes that share an engine, and MySQL-family routes on the same current database of one server share it as well. At the default Read Committed isolation level, a waiting registration reads the shared index state after the earlier registration commits. The `dolt`, `seekdb` and `oceanbase` types take no such lock, because their servers have no lock that writers can hold together while a registration waits for them: dolt takes no locks at all, and seekdb and OceanBase have only exclusive row locks (`LOCK IN SHARE MODE` takes one too), no gap locks, and no table locks (`LOCK TABLES` has no effect), so the only lock left would also hold every write of the entity off every other one. Nor do `mssql`, whose lock has not been run against a SQL Server, and the generic `sql` type, which can reach any server. On those types a row writer that validated before another rebuild committed can still use the old options, and a competing row write can cause a rebuild to fail with a unique-key error. Use the same entity definitions and options across workspaces. If the registration becomes stale, register it again with `allow_replace=True` or release and reopen the workspace.

An engine that may commit each statement keeps no shared keyword index and scans for `contained_in` with the field's configured sparse-GRAM options. So do the `pgvector` and `starrocks` backend types: HeavenBase 0.1.2.2 kept no index for them and still writes their rows without one, leaving no mark that it did, so an index kept by this release could not be trusted. Every route still checks that no index it does not maintain covers the entity, so a write through such a route is refused once another workspace indexes a field of the entity, whenever that index was created (with the Oracle `SERIALIZABLE` and MySQL `READ COMMITTED` exceptions above).

The adapter keeps the stored index state it last read for each entity: whether the index tables exist, the entity's fingerprints and its epoch, which every change of those fingerprints replaces. Registration reads it; a write after this route itself retired an index of the entity, or created the index tables for another entity, reads it once more. On the `sqlite`, `duckdb`, `postgres`, `pgvector`, `mysql`, `dolt`, `seekdb`, `oceanbase` and `oracle` backend types, on a route that declares atomic upserts, a write checks itself against that state and lets its first row statement for the entity check that the state is unchanged: a `DELETE` or an `INSERT ... SELECT` (on Oracle, a conditional `INSERT ALL`) that matches only while the index tables are still absent, the entity still has no epoch, or its epoch is still the one read. The condition holds for every row of a statement or for none, so a `DELETE` that removes any row confirms the state. A write whose state is unchanged therefore sends only its row statements, as in HeavenBase 0.1.2.2: five single upserts of a plain entity on `postgres` send 10 statements. When a write call's `DELETE` on a table removes none of the rows it names, because they are all new, the call inserts its first row into that table on its own, so it sends one statement more than 0.1.2.2 for each such table that gets more than one row. The Catalog table of a workspace write counts as well: a workspace `upsert_many` of several new rows of an entity with Catalog rows sends two more. A call that inserts one row per table, or that replaces at least one stored row of each table, sends none more. When the condition does not match, the write reads the state again with one query, is checked against it, and repeats the statements the condition held back; a refusal rolls the write back. A delete of a row that is not stored reads the state the same way. On a route of those types without atomic upserts (an engine that may commit every statement, or tables whose storage engine keeps no transactions), only the call's first row statement carries the condition, so a refusal still comes before any row is written: a call that replaces a stored row sends no query of its own, and one whose first `DELETE` removes no row reads the state with one query at once. A registration that commits after that first statement is not seen by the rest of the write where its statements commit on their own; carrying the condition on every statement would only refuse the rest of a write whose first statements had committed, such as a row deleted and not inserted again. On the other backend types (`starrocks`, `mssql` and the generic `sql` type) each write call sends one query for the check: the index-table lookup while those tables are absent, otherwise one read of the stored fingerprints and epochs of the call's entities. The first such read after another workspace creates the tables sends both. Within one transaction a later write call reuses what an earlier one read for the same entities. On a route that declares atomic upserts this read runs inside the write transaction after the row statements, and a refusal rolls them back. On a route without them it runs before the row statements; where these commit on their own, a registration that commits in between is not seen by that write. The generic `sql` type has no portable form of the condition or the lock: whether the index tables exist can only be asked of each server's own catalog (SQLite and Oracle have no `information_schema`), the row count a statement reports and the form of an `INSERT` of bound values differ by driver and server, and the server behind a dialect's URL need not accept the SQL of that dialect's own backend type. Name the server's own backend type to get the condition and the lock. Registration on an engine that keeps no keyword index can retire an index for the field. The adapter marks an unmaintained field before attempting retirement and refuses a conflicting mutation before the mutation commits. Retirement deletes the fingerprint before deleting keyword rows. If a partially committed retirement leaves rows without a fingerprint, a transactional registration rebuilds from the stored rows.

### Opening a store in HeavenBase 0.1.2.2

HeavenBase 0.1.2.2 stored a separate index under each workspace and backend namespace. It derived keyword IDs without the namespace. The current shared index includes the namespace in the ID and can coexist with those older indexes. When exactly one older index needs to be rebuilt, registration takes its rows into the shared index and retires the older index with a marker. For a field first indexed in this release, the first workspace to register it supplies the only marker. On downgrade, 0.1.2.2 rebuilds that workspace's index from the stored rows. Other workspace IDs without an index can open with an empty index.

When several 0.1.2.2 indexes exist, a fresh registration or registration with `allow_replace=True` rebuilds the shared index from the stored rows and preserves the legacy keyword rows. A legacy write can restore an earlier value while leaving its legacy keyword IDs unchanged. Rebuilding every legacy index over every row would create duplicate legacy keyword IDs. A previously retired namespace can reopen with an empty index when its stored fingerprint matches the options requested by 0.1.2.2. Each retained legacy index still sees only the rows it indexed. Avoid using 0.1.2.2 against the same database while this release writes to it.

### Publication and Catalog maintenance

SQL keyword changes are staged during schema publication. A rebuild and its eligible legacy retirement commit together. One registration can change existing indexes in several independent transactions. Transactions that change an existing index fingerprint or update legacy index retirement state commit after the other staged SQL transactions. A rebuild under the same fingerprint can repair the index for existing registrations and follow the ordinary commit order when legacy retirement state stays the same. A failure rolls back open transactions. Committed index changes can remain. SQLite and in-memory replacement recovery restore MetaSchema rows that still hold the failed publication's values. If a route cannot safely restore a row that needs recovery, it emits a warning.

Once registration publishes, pruning retires indexes that its bindings no longer use. A binding on another route to the same SQLite file or PostgreSQL index protects the stored index. Workspace mutations combine the row fragments of compatible PostgreSQL routes that share the same index and main table, and maintain those routes' indexed fields in the row transaction. A mutation with an unmaintained shared index is refused. On reopen, a change from `catalog="none"` checks the stored routes for IDs that fit in Catalog before publishing the incoming schema. A failed GRAM-only change can reattach a matching definition without rewriting its stored MetaSchema.

A `RowOp` with `strategies=False` skips keyword maintenance: it asserts that the row holds no indexed value, so it writes no keyword rows. Identity Catalog writes use this when the merge lookup finds no stored row or when the write is in fresh mode. After its row statements, in the same transaction, such a write still deletes whatever keyword and posting rows its object has, reading the latest committed keyword rows (with an exclusive lock on the `mysql` backend type), so a row that a concurrent full writer created with keywords after the lookup loses them with the write that replaces it; a write that finds none sends one query. An identity write replacing a row found by the merge lookup clears keyword rows written before it, including rows added after the lookup. `ws.audit()` compares the keyword and posting rows of every Catalog key in its scope with the rows its stored Catalog row indexes and lists a key whose rows differ under `stale_keywords`; `ws.repair()` writes such a row again with keyword maintenance.

## Performance Probe

The original 100K demo stress run preserved every unigram/bigram and wrote each row in its own transaction. It produced about 1.8M postings for 101K rows, with local timings around build `555s` and query `13.7s`.

The interim sparse policy (`postings_per_keyword: 4`) reduced the same run to 400K postings and query latency around `0.24s`, but profiling showed query time was still dominated by Python-side posting-list materialization.

The current trigram sparse-cover default (`gram_width: 3`, `sparse_grams_per_keyword: 0`) preserves all generated sparse spans and uses SQL aggregate candidate coverage. A local private stress probe produced 492,678 postings for 100K rows, with build `45.92s`, add 1K `1.16s`, replace 1K `1.30s`, delete 1K `0.65s`, and query `0.035s` for one 20-word query. The public demo intentionally does not expose stress knobs or sparse-GRAM tuning.
