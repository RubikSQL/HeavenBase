# HeavenBase Benchmark System Guide

## Purpose

The new HeavenBase benchmark system is designed to answer one question cleanly:

> Given the same workload, how do different backend combinations behave for build, query, edit, removal, and resource usage?

The old benchmark model mixed unrelated costs together and allowed different backends to run different operations. The new system fixes that by making the comparison target a backend combination and by running the same semantic workload across all selected combinations.

This makes the benchmark useful for:

- provider and index optimization
- regression checks after router or handler changes
- storage and memory footprint comparisons
- comparing pure SQL, pure in-memory, mixed scalar/vector storage placement, and search-backed combinations

## System Layout

The benchmark ships as package code under [src/heavenbase/benchmark/__init__.py](../../../src/heavenbase/benchmark/__init__.py), not as a one-off script.

The main pieces are:

- [src/heavenbase/benchmark/__init__.py](../../../src/heavenbase/benchmark/__init__.py): package facade that lists the public benchmark API and owns its lazy model, scenario, runner, and report route map
- [src/heavenbase/benchmark/model.py](../../../src/heavenbase/benchmark/model.py): result data model for stages, runs, resources, buckets, and aggregated summaries
- [src/heavenbase/benchmark/scenario.py](../../../src/heavenbase/benchmark/scenario.py): workload definitions and the default benchmark scenario
- [src/heavenbase/benchmark/meta.yaml](../../../src/heavenbase/benchmark/meta.yaml): declarative benchmark recipes installed through the same module catalog as external recipes
- [src/heavenbase/benchmark/combination.py](../../../src/heavenbase/benchmark/combination.py): immutable recipe model and Context-owned module-catalog resolution
- [src/heavenbase/benchmark/runner.py](../../../src/heavenbase/benchmark/runner.py): Context-bound timing, resource sampling, and orchestration
- [src/heavenbase/benchmark/report.py](../../../src/heavenbase/benchmark/report.py): JSON payload generation and Markdown composition
- [scripts/benchmark.py](../../../scripts/benchmark.py): thin CLI wrapper around the package API
- [scripts/benchmark.bash](../../../scripts/benchmark.bash): convenience launcher that activates the env, forwards the common knobs, and writes `BENCHMARK.md` by default

At the package level, the public entry points are:

```python
from heavenbase.benchmark import (
    BackendCombination,
    BenchmarkReport,
    BenchmarkRunner,
    BenchmarkScenario,
    DefaultProductScenario,
)
```

`BenchmarkRunner` requires an explicit `Context`. That Context is the single
authority for benchmark settings, recipe resolution, Backend construction, and
temporary workspaces; package code never reaches through `CM_HVNB` or
`DEFAULT_CONTEXT` implicitly.

## Benchmark Model

The benchmark compares backend combinations, not single backends in isolation.

A combination is a storage layout such as:

- pure in-memory
- pure SQLite
- SQLite for scalar fields plus in-memory vectors
- in-memory rows plus SQLite vectors
- SQLite plus a vector backend such as Lance, Chroma, or Milvus
- Elasticsearch for scalar and text fields plus an in-memory vector placement

Each selected combination runs the same workload semantics. If a backend cannot support an operation cleanly, that shows up as a stage error in the report instead of being silently skipped.

The aggregated result model is organized around four objective buckets:

- `build`: setup plus initial bulk upsert
- `query`: lookups, filters, vector near, hybrid near+filter, and counts
- `edit`: update or patch operations
- `removal`: delete plus post-delete validation

Resource samples are collected at four checkpoints:

- `before_build`
- `after_build`
- `after_edit`
- `after_removal`

Each sample records best-effort process RSS and backend-path disk usage when local paths exist.

## Default Scenario

The bundled default workload is [DefaultProductScenario](../../../src/heavenbase/benchmark/scenario.py).

It creates a product-like entity with these fields:

- `id`
- `name`
- `body`
- `price`
- `stock`
- `status`
- `category`
- `rating`
- `emb`

Rows are deterministic. Scalar data comes from a fixed template pool, and embeddings are generated by `StableRNG` using the benchmark seed.

By default, the scenario runs:

- build stages:
  - `setup`
  - `bulk_upsert`
- query stages:
  - `batch_get_many`
  - `batch_exists_many`
  - `point_lookups`
  - `point_get_entity`
  - `point_exists_entity`
  - `operator_getitem`
  - `operator_contains`
  - `workspace_count`
  - `workspace_len`
  - `iter_workspace`
  - `ids_entity`
  - `rows_entity`
  - `items_entity`
  - `filter_gt`
  - `filter_range`
  - `filter_text`
  - `filter_bool_tree`
  - `complex_query`
  - `vector_near`
  - `hybrid_query`
  - `count_all`
- edit stages:
  - `batch_set_many`
- removal stages:
  - `batch_delete_many`
  - `count_after_delete`

This is the fairness contract of the new system: same semantic matrix, different backend combinations.

## Registered Combinations

Bundled recipes are ordinary `benchmark_combination` module records in
[src/heavenbase/benchmark/meta.yaml](../../../src/heavenbase/benchmark/meta.yaml).
`BackendCombination.load(..., resolver=context.modules())` and
`BackendCombination.list(resolver=context.modules())` require a Context-owned
module resolver. An external module folder can publish the same record kind
without a HeavenBase source edit.

The dependency-light `default` suite contains:

- `inmem_all`
- `sqlite_all`
- `sqlite_inmem_vec`
- `inmem_sqlite_vec`

Additional registered suites contain:

- `sqlite_lance_vec`
- `lance_all`
- `sqlite_chroma_vec`
- `chroma_all`
- `elasticsearch_inmem_vec`
- `sqlite_milvus_vec`
- `milvus_all`
- `pgvector_all`
- `mysql_all`

These recipes remain inspectable even when an optional SDK or service is not
available. Selecting one produces honest setup or stage evidence instead of
silently changing the catalog. Backend connection details come from the
runner's Context configuration under `heavenbase.backend_defaults`.

The intent of each combination is visible through its storage fields:

- `scalar_backend`: where scalar business fields go
- `vector_backend`: where the embedding field goes
- `resource_paths`: which directories should be sampled for disk usage

`elasticsearch_inmem_vec` exists because Elasticsearch is useful for scalar and text query benchmarking, while the default benchmark still requires a working vector placement for `near` and hybrid stages.

## Running the Default Script

The common entry point is [scripts/benchmark.bash](../../../scripts/benchmark.bash).

From the repo root:

```bash
bash scripts/benchmark.bash
```

That wrapper:

- uses the repository's standard Python environment resolver
- forwards every argument unchanged to the Python CLI
- leaves per-run resource cleanup to `BenchmarkRunner`, so concurrent runs do not delete one another's paths

Unless the selected Context overrides them, the CLI defaults are:

- scales: `1,10`
- repeats: `5`
- seed: `42`
- report path: `BENCHMARK.md`

Common commands:

```bash
# Default run, writes BENCHMARK.md in the repo root.
bash scripts/benchmark.bash

# Fast sanity check.
bash scripts/benchmark.bash --scales 1 --repeats 1

# Only run a subset of combinations.
bash scripts/benchmark.bash --combinations inmem_all,sqlite_all,elasticsearch_inmem_vec

# Keep a JSON artifact too.
bash scripts/benchmark.bash \
  --combinations inmem_all,sqlite_all,elasticsearch_inmem_vec \
  --artifact benchmark.json \
  --report BENCHMARK.md

# Preserve a report even when some optional backend stages fail.
bash scripts/benchmark.bash --allow-errors
```

## CLI Options

The full CLI surface lives in [scripts/benchmark.py](../../../scripts/benchmark.py).

Supported flags are:

| Flag | Meaning |
|---|---|
| `--scales` | Comma-separated scale factors |
| `--repeats` | Repeats per scale |
| `--seed` | Deterministic RNG seed |
| `--combinations` | Comma-separated registered combination identifiers |
| `--base-rows` | Base row count before scale multiplication |
| `--vector-dim` | Vector dimension for the default scenario |
| `--top-k` | `top_k` for near search stages |
| `--temp-root` | Temp directory root for backend artifacts |
| `--artifact` | Optional JSON artifact path |
| `--include-raw` | Include per-repeat raw runs in JSON |
| `--report` | Markdown report path |
| `--allow-errors` | Write reports even if one or more stages fail |

The same flags work through either entry point. Calling the Python CLI directly is also valid:

```bash
rtk uv run python scripts/benchmark.py \
  --scales 1 \
  --repeats 1 \
  --combinations elasticsearch_inmem_vec \
  --base-rows 500 \
  --vector-dim 256 \
  --top-k 20 \
  --include-raw \
  --artifact benchmark.json \
  --report BENCHMARK.md
```

## What the Report Means

The generated Markdown report has two levels:

1. a summary table per combination and scale
2. a detailed section per combination and scale

The summary focuses on:

- build time
- query time
- edit time
- removal time
- build-time memory delta
- build-time disk delta

The detailed section includes:

- backend identifier mapping such as `main=sqlite`, `vec=inmem`
- resource samples at each checkpoint
- every aggregated stage with mean, std, samples, rows, throughput, latency, and notes

Interpretation rules:

- lower `build` means cheaper setup plus ingest
- lower `query` means better read and search performance across the full matrix
- lower `edit` means cheaper updates
- lower `removal` means cheaper delete and post-delete validation
- higher throughput is better
- lower latency is better
- resource deltas show storage and memory growth rather than only raw totals

If a stage fails on some repeats:

- the report still records the error details
- aggregated means exclude failed repeats, and every mean publishes the `samples/repeats` it covers
- a repeat that aborted before reaching a stage is excluded the same way, never averaged in as zero seconds
- a stage no repeat measured prints `-` rather than `0.000`, and the bucket total says how many of its stages it covers
- a resource delta is published only when both checkpoints averaged the same repeats, because subtracting means taken over
  different populations measures the population rather than the phase
- notes explain whether the stage is partial or fully failed

## JSON Artifact

If `--artifact` is set, the report can also be emitted as structured JSON.

The JSON contains:

- `meta`
- aggregated `combinations`
- optional `raw_runs` when `--include-raw` is enabled

Aggregated runs include:

- bucket summaries
- stage summaries
- resource samples
- resource deltas

This is the recommended source for:

- CI regression gates
- plotting benchmark histories
- provider-specific performance analysis
- external dashboards

The Markdown file is the human view. The JSON file is the machine view.

## Using the Python API

The package API is the right choice when you want to benchmark custom combinations or a custom workload.

### Run the default suite programmatically

```python
from heavenbase import DEFAULT_CONTEXT
from heavenbase.benchmark import BenchmarkRunner

report = BenchmarkRunner(DEFAULT_CONTEXT, scales=[1], repeats=1).run()
report.write_markdown("BENCHMARK.md")
report.write_json("benchmark.json", include_raw=True)
```

### Run selected registered combinations

```python
from heavenbase import DEFAULT_CONTEXT
from heavenbase.benchmark import BenchmarkRunner, DefaultProductScenario

runner = BenchmarkRunner(
    DEFAULT_CONTEXT,
    scenario=DefaultProductScenario(base_rows=500, vector_dim=256, top_k=10),
    combinations="inmem_all,sqlite_all,elasticsearch_inmem_vec",
    scales=[1, 10],
    repeats=3,
    seed=42,
)
report = runner.run()
```

### Define a custom backend combination

```python
from heavenbase import DEFAULT_CONTEXT
from heavenbase.benchmark import BackendCombination, BenchmarkRunner

combo = BackendCombination(
    label="elastic_custom_vec",
    combination_type="search+vector",
    backends={
        "main": {"type": "elasticsearch"},
        "vec": {"type": "inmem"},
    },
    scalar_backend="main",
    vector_backend="vec",
)

report = BenchmarkRunner(DEFAULT_CONTEXT, combinations=[combo], scales=[1], repeats=1).run()
```

Direct objects are convenient for one process. To make a recipe installable and
discoverable, publish the same declarative fields as an inline
`benchmark_combination` item in a module folder's `meta.yaml`.

### Define a custom scenario

Subclass `BenchmarkScenario` when you need your own entity, row generator, or operation matrix.

```python
from heavenbase.benchmark import BUCKET_EDIT, BUCKET_QUERY, BUCKET_REMOVAL, BenchmarkOp, BenchmarkScenario


class TicketScenario(BenchmarkScenario):
    label = "tickets"
    base_rows = 5_000
    vector_dim = 128

    def make_entity(self, ctx, combination):
        ...

    def make_rows(self, n, rng):
        ...

    def query_ops(self, ctx):
        return [
            BenchmarkOp("open_tickets", BUCKET_QUERY, lambda: ...),
        ]

    def edit_ops(self, ctx):
        return [
            BenchmarkOp("status_patch", BUCKET_EDIT, lambda: ...),
        ]

    def removal_ops(self, ctx):
        return [
            BenchmarkOp("archive_delete", BUCKET_REMOVAL, lambda: ...),
        ]
```

When you customize the scenario, keep the benchmark honest:

- keep operation semantics stable across combinations
- keep the seed deterministic when comparing runs
- keep row counts large enough to expose meaningful costs

## Recommended Workflow

For day-to-day work:

```bash
bash scripts/benchmark.bash --scales 1 --repeats 1 --combinations inmem_all,sqlite_all,elasticsearch_inmem_vec
```

For a more meaningful provider comparison:

```bash
bash scripts/benchmark.bash --scales 1,10 --repeats 3
```

For regression tracking in a branch:

1. run the benchmark before the optimization
2. save JSON and Markdown
3. apply the change
4. rerun with the same seed, scales, repeats, and combinations
5. diff the JSON or compare bucket totals and stage-level metrics

For backend-specific diagnosis:

- start from bucket totals
- drill into stage rows inside that bucket
- use resource deltas to separate compute wins from storage or memory regressions

## Troubleshooting

| Symptom | Meaning | What to do |
|---|---|---|
| report generation exits non-zero | one or more benchmark stages failed | rerun with `--allow-errors` to keep the report, then inspect the failing stages |
| an optional combination is absent from the default run | only the `default` Registry suite is selected implicitly | pass its registered identifier with `--combinations`, or inspect `BackendCombination.list(resolver=context.modules(), suite=None)` |
| Elasticsearch combination fails on setup or query | Elasticsearch is not reachable at the configured hosts | start the service or set `heavenbase.backend_defaults.elasticsearch.hosts` accordingly |
| SQL or vector server combinations fail | service is not ready | start the corresponding Docker or local service first |
| disk delta looks flat | backend stores outside sampled paths or uses server-side storage | treat local disk sampling as best-effort |
| memory delta is missing | `psutil` could not sample RSS | install or restore the runtime dependency |

## Practical Rule of Thumb

Use the bash wrapper for the normal repo environment setup. It forwards the
complete Python CLI surface unchanged.

Use the package API when you want to benchmark your own backend combination or your own workload scenario.
