# 0.1.2.3 - 2026.11.25

- **Behaviour changes for 0.1.2.2 users** (read first):
  - `Timestamp.validate(None)` raises `ValueError` instead of substituting the current time. Pass `datetime.now(timezone.utc)` for "now" and declare nullable fields `.optional()`. Query filters on a Timestamp field, including Catalog `created_at`/`updated_at`, keep `None` for `== None`, `!= None`, `{field: None}`, `$ne` and `$in` and test for a missing value; 0.1.2.2 compared them with the current time.
  - An order filter (`$lt`, `$lte`, `$gt`, `$gte`, or the corresponding comparison operators) given `None` raises `ValueError` on every field type that supports order filters. Use equality, inequality or membership to test for a missing value. 0.1.2.2 compared Timestamp with the current time, compared text fields against an empty string, and could fail in the type or provider on other ordered fields.
  - `hb.DEFAULT_CONTEXT` is built on first use, not on import, so `import heavenbase` no longer reads the personal bootstrap; `heavenbase.context.set_default_context(context)` installs an explicit root Context before that. A root Context built with `Context.load(..., config=hb.CM_HVNB)` before first use becomes that default on first use; once it is closed without being installed, first use raises `RuntimeError`. After `set_default_context` installs a Context with its own config, a backend, `BackendRegistry` or `BackendType.build` given neither config nor resolver uses that Context's config and modules. So do `Predicate.compile()`, `HandlerContext()`, profile resolution, and toolkit and query helpers that omit their config. Standalone `Database`, SQL backend, `LLMEngine` and Capsule calls (such as `capture_function` and `CapsuleAuthority.resolve`) given `CM_HVNB` alone use its owning Context's config and resolver, or the installed default Context's pair when `CM_HVNB` is unowned. Explicit pairs must still match. Explicit Context mode still requires explicit authority. `BackendRegistry` and `BackendType.build` still raise `ValueError` for a config given without a resolver. Assigning `heavenbase.context.runtime.DEFAULT_CONTEXT = context` before first use installs the default as `set_default_context(context)` does; after first use it replaces the default in use, as rebinding the global did in 0.1.2.2. `mock.patch.object(runtime, "DEFAULT_CONTEXT", context)` can swap and restore the default without selecting one first. `monkeypatch.setattr` reads the current value before setting it, so it selects a default when none is in use and raises in explicit Context mode. Deleting the attribute restores the Context in use before the first assignment, or no default. A first access to `hb.DEFAULT_CONTEXT` or `heavenbase.context.DEFAULT_CONTEXT` during the patch caches the patched Context in that facade. Use `runtime.default_context()` to read the live default. First installation and implicit adoption require an open root. After selection, `set_default_context` accepts the same open root again and raises `RuntimeError` for a different root. Default CLI commands use the installed Context and its configuration. A missing CLI backend setting falls back to the packaged Typer default. `DEFAULT_CONTEXT` is no longer in the `__all__` of `heavenbase` or `heavenbase.context`, so a star import does not bind it. Both facades list `DEFAULT_CONTEXT` in `dir()` before lazy initialization. A Context installed with `set_default_context` after its first cached LLM call keeps its one `LLMCache` and that cache's store, and `LLMCache.reset(config_manager=...)` retires that cache. Any access to a Registry-backed entity export of `heavenbase` or `heavenbase.extensions.agent_log` (`hb.Agent`, `from heavenbase import Agent`, `from heavenbase.extensions.agent_log import AgentTrace`, a star import of either module, or `inspect.getmembers()` on it) still loads the class through the default Context. In normal mode it builds that Context from the personal bootstrap, creating `~/.heavenbase` on a fresh `HOME`, and it raises `KeyError` for an entity that the selected registry does not hold. In explicit Context mode it raises `RuntimeError`. An explicit-mode application therefore takes these classes from its own Context, not from the package facades: from a workspace that enables their extension (`ws.entities["agent-agent"]`), or, without a workspace, through `load_entity_type("agent-agent", resolver=context.modules())` from `heavenbase.entity.registry` once `context.modules().setup()` has run. Importing a class from the module that defines it, such as `heavenbase.extensions.agent_log.trace`, gives a class that is not the one the Registry restores, and a workspace refuses several of them, `AgentTrace` included, with `ValueError` (see the Registry and Context architecture page). After `set_default_context` installs a Context with its own config, `heavenbase.api.run_server()` and `heavenbase.dashboard.serve()` called without `api=` read the session-log boot check, host and port from that Context's config, and `serve()` also reads `heavenbase.dashboard.open` there when `open_window` is not given. `heavenbase.api.resolve_bind()` called without `cm` reads host and port from that config. That is the config the served `DashboardAPI()` uses; before, they read `CM_HVNB`.
  - Workspace reads no longer take the Context lock. A read of one workspace now runs while another workspace of the same Context is being written, where 0.1.2.2 ran every workspace call of a Context one at a time; code that relied on that serialization across workspaces needs its own lock. Writes are still serialized per Context. Facades of one workspace id in one Context tree share one lock, so a write through one of them still waits for, and holds back, reads and writes through the others. A detached facade has its own lock, so its reads no longer wait for writes through other facades of the same workspace id, and their reads no longer wait for its writes; 0.1.2.2 ran all of them one at a time under the Context lock.
  - `Context.close()` and `reset_default_local_state()` called by a thread that holds no Context or workspace lock wait, for at most 30 seconds in all, for work of other threads that they must not overlap. They first wait for another thread's hold of the Context lock (such as a write), which is reserved for them while they wait for it, so they get it as soon as its holder lets it go; close also waits for a reset that another thread runs. Then they mark the Context, so that new operations and workspace calls fail, as in 0.1.2.2, and wait for the root's resolver operations that are already running, which go on with the resolver operations they nest, and, for a reset that would remove storage, for the workspace reads already running. When all of this ends in time, they go ahead; otherwise they raise `RuntimeError` and leave the Context as it was, so that operations work again. In 0.1.2.2, close and reset waited without a limit for the Context lock, close also waited for a running close or reset, and both waited without a limit for other threads' running resolver operations. A caller that holds a Context or workspace lock is refused at once, except that it may close an idle child with no owned backend to dispose when the child's shared Context lock is immediately available; one that runs a database drop is refused at once if it would have to wait; so is a close or reset from a resolver operation of the same root, also while another thread holds the Context lock, and a close by a thread with a database connection in use while another thread resets the Context. Admitted reads can finish or fail as their resources retire.
  - `upsert` reads the keywords `overwrite` and `atomic` as write flags, each a bool, unless the row's Entity class declares a field of that name; the keyword is then that field's value, and such an entity passes the flag to `upsert_many`, which takes `overwrite` and `atomic` as flags only. For a declared `atomic` field this is 0.1.2.2 behaviour. For any other entity, 0.1.2.2 silently dropped an `atomic` keyword as an undeclared field. Now a non-bool value raises `TypeError`, and a bool value is honoured, so `atomic=True` on a write whose routes span backends raises `ValueError`. 0.1.2.2 always read an `overwrite` keyword as the replace flag, using its truth value, so for an entity that declares a field named `overwrite` the keyword's value never reached the field. Now that keyword is written as the field, and the row replaces an existing one by default. For other entities a non-bool `overwrite` keyword raises `TypeError`.
  - In-engine `LIKE`/`ILIKE` follow SQL: `%` and `_` match across line breaks and the pattern must match the whole value, so a value with a trailing newline no longer matches a pattern without one.
  - The portable `near` scan (the route used when no native vector search applies) ranks by the requested `metric` (`l2`/`euclidean`, `ip`/`inner`/`inner_product`/`dot`) instead of always by cosine. An unknown metric raises `ValueError` instead of falling back to cosine; 0.1.2.2 also read `dot` as cosine there. On a backend without native vector search, a row with no vector is left out under a non-cosine metric rather than scored `0.0`, which ranked it above every real neighbour. Cosine keeps the 0.1.2.2 score of `0.0`, and `exact=True` leaves the row out. On a backend with native vector search (LanceDB, Chroma, Pinecone, pgvector, RediSearch, Milvus, Qdrant, Weaviate, Neo4j, SurrealDB), a near whose filter cannot be pushed down uses a scan when the route can supply the required rows. That scan now ranks by the requested metric and leaves such a row out under every metric, as native search does. In 0.1.2.2 the Lance, Chroma, Pinecone and pgvector scan scorers ranked by cosine and RediSearch ranked by the index metric, and under cosine every one of these scans scored the row `0.0`, so a filter that admitted every row could put it in place of a real neighbour.
  - Every native Milvus vector search requests Strong consistency, as Milvus scans and point lookups already did, so a search sees writes made just before it at the cost of extra latency per search.
  - `hb.ResultFrame.project` raises `ValueError` for a column the frame does not hold, even when the frame is empty; 0.1.2.2 added such a column as an empty column on an empty frame. Build an empty frame with its columns through `ResultFrame.empty(cols)`.
  - Row-query results without `select` carry identity, every declared field, filter metadata such as `match`, and finally the `score` for a near query, even when no rows match. A declared field that no matched row stored reads as null when selected or ordered. In 0.1.2.2, empty results carried only `object_id` and selected columns, a populated result could omit unstored fields, and `score` could appear before later columns.
  - The first access to `hb.CM_HVNB` selects the process default Context: a direct read or write, a HeavenBase log record, `hash_id` without `length=`, `StableRNG` without explicit hash settings, serialization or parallel helpers, or a backend, `Database`, `LLMEngine` or `LLMCache` whose config falls back to `CM_HVNB`. The process then reads the values saved with `hb config set`, and its `CM_HVNB.set` calls persist to the HeavenBase home; 0.1.2.2 read only the packaged defaults when such an access came before the default Context, and kept those writes process-only. Global log helpers (`configure_logs`, `set_log_level`, `redirect_logs`, `suppress_logs` and `restore_logs` without `loggers=`) apply changes to the calling process by default. Use `persist=True` or `hb config set` to write the default Context's configuration. Other processes sharing that store see saved changes after their config cache refreshes (`heavenbase.config.cache.refresh_interval`, 2 seconds by default). In 0.1.2.2, `set_log_level()` could change the level seen by other processes once `DEFAULT_CONTEXT` had bound `CM_HVNB` to persistent storage. Like every default-Context path, the first access creates the package home on a fresh `HOME`. An unwritable home or an unusable bootstrap (it fails validation, names a backend module or driver that cannot be imported or settings its backend rejects, or holds an invalid Registry hash policy) makes `CM_HVNB` warn once and use the packaged defaults with process-only edits, as 0.1.2.2 did. Check `ConfigManager.last_write_persisted` after a mutation; CLI config mutations exit nonzero when changes stay local. A refresh retries the store and keeps local edits; pass `refresh(discard_process_changes=True)` to replace them once a persistent store is available. Explicit Context binding and reset retire the temporary scopes. In explicit Context mode a read or write of an unowned `CM_HVNB` raises. Any other failed open, such as a database that stays locked, is not remembered: `hash_id` and the RNG raise it, log records and the serialization and parallel helpers use their defaults for that call, and the next access tries again. On an unwritable home the failed open also logs a `Database autocreate failed` warning. Call `hb.configure_explicit_context()` or install a different root with `set_default_context` before using a utility that selects the default.
  - Package facades are lazy. Importing a HeavenBase package no longer imports its submodules; each export is loaded on first access, and `package.submodule` imports the submodule on first access, as `import heavenbase.placement as p; p.scalar` did in 0.1.2.2. An import error now comes on first access instead of at package import: a submodule that needs a missing optional dependency raises `AttributeError` with the `ImportError` as its cause, and an export whose module fails to import raises that `ImportError` (so `hasattr(package, name)` raises it too). `vars(package)` holds an export only once it has been read, and `dir(package)` also lists every submodule, so `inspect.getmembers(package)` imports them all. `heavenbase.placement.index` stays the `index()` function. Internal modules no longer hold names they imported only for their own use: `heavenbase.context.reset.DEFAULT_CONTEXT`, `heavenbase.workspace.setup.lifecycle.DEFAULT_CONTEXT`, `heavenbase.execution.contracts.deepcopy` and `heavenbase.workspace.catalog.rows.deepcopy` are gone; use `hb.DEFAULT_CONTEXT` and `heavenbase.utils.deepcopy`. Concurrent first imports no longer deadlock inside HeavenBase, and `import heavenbase` now also imports `asyncio` to settle a known third-party import-lock cycle (see Concurrent first use below).
  - The dashboard assistant's default model is the `chat` preset instead of `deepseek-v4-pro` from the `deepseek` provider.
  - An unfinished `SQLResponse` iterator that is freed by a garbage collection (a reference cycle) no longer drains and closes its response inside the collection. The new `heavenbase-sqlresponse-settler` daemon thread does it soon after. Since `Database.execute` now streams only reads and commits every other statement before it returns (see below), this matters for a streamed read that writes through a function it calls, such as a PostgreSQL `SELECT f()` whose `f` inserts. 0.1.2.2 committed it inside the collection; it is now committed shortly after, on that thread, also when the response is dropped in the meantime. When the collection frees the response too, the settler reads the remaining rows without keeping them, and that connection stays checked out until it has; a drop on the thread that executed the response settles it first, on that thread. If `readonly` accepted the statement, the settler only rolls it back and releases it. At exit, a hook runs a garbage collection while such an iterator exists and then settles what is queued. An iterator that the interpreter's own final collection frees, after the exit hooks, still rolls back, as in 0.1.2.2. An iterator dropped outside a collection still drains and closes its response on the thread that drops it, as in 0.1.2.2. The exception is a thread that is itself inside a read of the same response: the settler drains it once that read ends.

  - On the Chroma backend, an entity whose Vector field Chroma stores needs that vector. A new row without it, or any row that sets it to `None`, raises `ValueError` naming the rows. 0.1.2.2 sent no embeddings for such a batch, so Chroma embedded every document in it with its default model.
  - Outside `db.tx()`, `Database.execute` and `orm_execute` stream rows lazily when they recognize a read. Other statements commit before returning and cache any reported rows, including `INSERT ... RETURNING`. In 0.1.2.2, a statement whose cursor reported rows committed when its response was consumed or closed, so dropping the response rolled it back and keeping it open could hold SQLite’s write lock. With the default `readonly=False`, a read that HeavenBase cannot confirm also caches its rows. Pass `readonly=None` or `readonly=True` to stream it when the read-only check accepts it. A read that writes through a function it calls can still stream. It rolls back if its response is dropped before it is drained or closed with no iterator over it; an abandoned iterator drains and commits it (see above). With `autocommit=False`, both methods require an active transaction. Outside one, `safe=True` returns a failed response.
  - `atomic=True` on `upsert` and `upsert_many` is refused with `ValueError` on a backend that does not claim the new `atomic-upsert` tag (see Atomic upsert below), including the generic `sql` type, `clickhouse`, `starrocks`, `trino`, `file`, `json`, `pickle`, Chroma and a SQL backend whose engine may commit every statement. 0.1.2.2 had no `atomic` flag.
  - Workspaces that resolve the same SQL sparse-GRAM storage tables share one index per entity field, built with one set of options: the field's `SparseGramIndex` options over the Context's `heavenbase.strategy_defaults.sparse_gram` defaults (see Shared sparse-GRAM index). When another workspace or process registers the field with other options, or without the index (`gram=False`, another placement, another type, or an entity definition without the field), the index is rebuilt with those options or deleted, and a later indexed `contained_in` query or indexed write through a backend registered with the earlier options raises `SparseGramIndexConflictError` (a `RuntimeError`, from `heavenbase.backends.sql.strategies`) instead of missing rows. A strategy-maintained mutation also raises if the writer lacks a binding for any currently indexed field, including fields added since it registered the entity, on every SQL route, also one that keeps no keyword index, except on an `oracle` engine at `SERIALIZABLE` for a write whose transaction began before another workspace started indexing the entity (see **Shared sparse-GRAM index** and **Keyword-index checks on writes**). In 0.1.2.2 each workspace kept its own index, which missed the other workspaces' writes. Use the same options and `gram` setting across workspaces that share those tables. PostgreSQL schemas in one database can have separate indexes. Registering the entity again with `allow_replace=True` rebuilds the index with that registration's options; so does opening the workspace again after releasing it (`HeavenBase.load(id)` returns the open facade until it is released).
  - A SQL engine that may commit every statement keeps no sparse-GRAM keyword index. `contained_in` scans its stored rows using the field's `SparseGramIndex` options. A registration there can retire the shared keyword index, and a strategy-maintained mutation is refused before any row is written if another workspace indexes the field, also when that index was created after the engine registered the entity. Workspaces sharing a Catalog database should use one engine mode. To keep an index, use a transactional SQL engine listed under **Atomic upsert** other than `pgvector`, which keeps none.
  - The SQL read guard is stricter for ambiguous text, writes embedded in read-like statements, and SQL Server batches that omit semicolons. SQLGlot, now included in the `full` extra, can recognize multiple unambiguous reads. Without SQLGlot or when it cannot classify the text, the lexical check recognizes at most one statement. The guard rejects `EXPLAIN ANALYZE` of writes and pragmas that change settings. See the database reference for exact classification rules.
  - File backends keep compatible encoded record names and use hashed names for long IDs, reserved device names, and case or short-name collisions. HeavenBase 0.1.2.2 can scan records under hashed names but cannot find them by ID.
  - Pinecone requires exactly one routed Vector of known dimension matching the index. A vectorless upsert can remove the Pinecone record when the remaining Pinecone metadata values are null and routes that retain the row preserve every required or defaulted field. Otherwise it raises `ValueError` before any route is written. Patches and GraphEdge rewrites require a readable source on each Pinecone route. A fetch miss raises before mutation, with guidance to retry or use a full upsert where applicable. A Pinecone fetch miss does not show that a row is absent, and only the entity's oldest routes can show it: a route on any other backend that is one of them keeps every row written to it. When all of the entity's oldest routes are on Pinecone, the miss is inconclusive, also when a newer route is on another backend. For such an entity, entity inference over it (also when no other entity holds the ID), `set` of a new ID, confirmed GraphEdge repair of a missing target, and `upsert`/`upsert_many` with `overwrite=False` for any ID that no route returns raise `ValueError` before writing: Pinecone documents no bound on when a write becomes readable, and its read-after-write check needs the write's log sequence number, which a reader has only for its own writes, so a miss cannot show that a record another client or an earlier process wrote is absent. A GraphEdge delete of such a missing target restricts or detaches its incoming references as for a present target, deletes its record and Catalog row, and returns `False` for it. In 0.1.2.2 such a create-only write of a new ID succeeded. Specify the entity explicitly when inference is inconclusive, and pass `overwrite=True` to write such a row. A route that `register(..., allow_replace=True)` adds holds only rows written after the change, so it does not show that a row is absent while the entity keeps an older route; when those older routes are all Pinecone, these checks raise as for an entity stored only on Pinecone. The entity's MetaSchema entity row records the later routes under `meta.route_generations`. Registrations made by 0.1.2.2 or earlier record none, so for a route such a release added, rewrite the rows stored before it with a full upsert, reading them by ID because Pinecone cannot list its records, before relying on these checks.
  - Portable regex filters estimate the Python match cost against the configured text limit. Expensive supported regular patterns run in the bounded matcher. Expensive patterns requiring unsupported constructs, including some patterns with lookaround or backreferences, can raise `ValueError` unless `heavenbase.query.regex.allow_nested_quantifiers` is enabled.
  - **Chroma near**: near() ranks by the requested metric, and near() without a metric requests heavenbase.query.near.default_metric (cosine). When the requested metric differs from the collection's effective embedding metric or the requested Vector is not its indexed embedding field, near uses the portable scorer. New collections record the embedding field and preserve it across schema registration. Older collections without a recorded field rely on the original declaration order. A collection that 0.1.2.2 wrote for an entity whose first declared Vector field is stored on another backend holds 384-wide embeddings that Chroma computed. When the first Vector field stored on Chroma declares another dimension, no field becomes the collection embedding: writes and patches work as in 0.1.2.2, Vector fields stored on Chroma are kept as metadata, and a near on one ranks the vectors written since through the portable scorer; 0.1.2.2 ranked the computed embeddings for a 384-wide query and raised for any other. With dimension 384, or none declared, the computed embeddings read as the field's vectors until the rows are upserted with their vectors, and an undimensioned field there takes only 384-wide vectors: declare its dimension. 0.1.2.2 searched natively by the collection space whatever metric was requested, so results and scores can differ. For collections of chromadb 0.6.3 and earlier see **Known issues**. Each near and explain() call opens the collection once to read its current space, when the near clause is compiled. Execution reuses that collection for the near clause itself and for hydrating its hits. A near whose filter has fields on two routes evaluates the Chroma part of the filter separately and opens the collection again. explain() reports py_scan with a fallback reason. A metric name outside cosine/l2/euclidean/ip/inner/inner_product/dot now raises ValueError; 0.1.2.2 ignored it. To keep native ranking on a non-cosine collection, pass metric=<collection space> or set heavenbase.query.near.default_metric to it.
  - **RediSearch near**: a near whose metric is not the metric of the existing FT index ranks through the portable scan, with or without a filter, and explain() reports py_scan. HB reads that metric with one FT.INFO per near or explain() call, when the near clause is compiled, so a native near sends one more command than in 0.1.2.2 and sees an index another client rebuilt; before the index exists it uses heavenbase.backend_defaults.redisearch.metric (default cosine). 0.1.2.2 ranked every near by the index metric. A metric name outside cosine/l2/euclidean/ip/inner/inner_product/dot now raises ValueError; 0.1.2.2 ignored it. Remedy as for Chroma: pass metric=<index metric> or set heavenbase.query.near.default_metric.
  - **Pinecone near**: a near whose metric is not the metric the index was created with raises ValueError, because Pinecone has no row scan. HB reads that metric from the live index description once per near or explain() call (one `has_index` and one `describe_index` request), when the near clause is compiled, and execution and hit hydration reuse it. This includes near() without a metric on a non-cosine index, since that requests default_metric cosine, and any metric name outside cosine/l2/euclidean/ip/inner/inner_product/dot. 0.1.2.2 answered with the index metric. Remedy: pass metric=<index metric> or set heavenbase.query.near.default_metric. Euclidean scores are now the negated value Pinecone reports, so a higher score is nearer; 0.1.2.2 returned the raw distance.
  - **Lance near**: metric='ip'/'inner_product'/'inner' and 'euclidean' now search natively, as LanceDB dot and l2; 0.1.2.2 raised RuntimeError. metric='dot' already searched natively. It now scores the inner product, where 0.1.2.2 scored the inner product minus 1, and it also works with exact=True. Native search uses the selected vector column, including for an entity with multiple Vector fields. Any other metric name raises ValueError.
  - **pgvector near**: a native near leaves out a row without a vector under every metric, as other native backends do. 0.1.2.2 placed the row last and scored it 1.0, a perfect cosine match. A metric name outside cosine/l2/euclidean/ip/inner/inner_product/dot raises ValueError; 0.1.2.2 ranked it by cosine.
  - The `full` extra and the Chroma backend now need chromadb 1.5.0 or later (`chromadb>=1.5.0`; 0.1.2.2 asked for `>=0.5`). It is the first chromadb whose metadata holds lists and whose `where` takes `$contains`, which Array fields and the native `array_contains` on Chroma rely on. Before 1.5.0 those failed on every chromadb release that was allowed. chromadb 1.0.0 and earlier also reject the `None` metadata value that an upsert now sends to clear a field. With an older chromadb the Chroma backend is unavailable: every operation raises `RuntimeError` naming the version it needs, before anything is written to Chroma.
  - A Chroma upsert replaces its stored fields while preserving an omitted vector. Setting a metadata field to `None` or omitting it clears its old value. An explicit null in a nullable metadata field with a default is stored as null. An empty Array reads back as `[]` and clears the old native list used for filtering. Membership on untyped Arrays and Arrays of Json uses the portable scan.
  - LanceDB upserts report a failed merge immediately. Earlier batches and other clients' commits remain in effect.
  - Milvus Lite ranks every exact query and ordinary cosine queries through a binary64 scan. Ordinary L2 and inner-product queries can use native search when the metric matches the index. Milvus stores scalar values in built-in `Json` fields using marked wrappers that HeavenBase 0.1.2.2 reads as objects.
  - `heavenbase.modules.tags` is now always the `tags()` function that `heavenbase.modules.__all__` lists, even after the `heavenbase.modules.tags` submodule has been imported, which every workspace build does. As with `heavenbase.placement.index`, `import heavenbase.modules.tags as m` now binds the function, not the submodule. String patch targets that go through it no longer reach the submodule. `monkeypatch.setattr("heavenbase.modules.tags.<name>", ...)` raises `AttributeError` on every Python version, and so does `mock.patch("heavenbase.modules.tags.<name>")` on Python 3.10. To reach the submodule, use `importlib.import_module("heavenbase.modules.tags")` or `from heavenbase.modules.tags import ...`, which are unchanged. Patch it with `monkeypatch.setattr(module, "<name>", ...)` or `mock.patch.object(module, "<name>", ...)`.
  - Entities that an enabled extension registers (such as `memory-note`, `agent-session`, or an entity its setup hook returns) keep the extension's definition. `alter_entity`, `describe` and `register` (with or without `allow_replace=True`) raise `ValueError` when they would change such an entity's structure, `catalog` or `gram` option, or metadata (name, descriptions, tags and examples); 0.1.2.2 accepted the change and silently undid it when the workspace reopened. A differing definition mapping for such an entity that cannot be compiled also raises the extension's `ValueError`, not the compiler's error (such as a `KeyError`). A call that changes nothing is accepted, including the definition mapping `to_manifest(include_system=True)` exports for an entity with derive or compute hooks (such as `agent-message` or `db-table`), which 0.1.2.2 rejected. A default manifest leaves out every extension entity, the entities a setup hook returns included, which 0.1.2.2 exported. Importing a manifest skips an extension entity's definition that has the extension's structure and options, without applying its name, descriptions, tags or examples (a `UserWarning` names those it states differently), and raises `ValueError` for any other definition of it, also with `allow_replace=True`. See **Extension entities keep their extension's definition** and **Manifests and extension entities** below.
  - A `reset_default_local_state()` whose hidden-store drop raises still retires the Context authority, so `LLM` objects and other services built before it raise 'belongs to a retired Context authority generation', as they already did after a successful reset. Build new ones after the reset.
  - During a `run_python` run that started while `sys.stdout` was None, threads outside runs see a null text stream and their writes are dropped; 0.1.2.2 captured them into the run's output. See **`run_python` namespace**.
  - A `run_python` run captures the output of its own thread and of threads started during it. Output of any other thread, such as a worker of a thread pool that an earlier run or the host created, goes to the host's stdout; 0.1.2.2 captured every thread's output while a run was active. User info is found when it is well formed, and also when it holds a `:` before its first unescaped `/`, `?` or `#` and no `@` before that mark: it then runs to the last `@` of the URL, so `postgres://user:pa/ss@host/db` is stored as `postgres://***:***@host/db`. User info that holds a `/` before its `:` (`postgres://us/er:pass@host/db`) ends at the last `@` before the query and fragment whenever a `:` comes before that `@`, and so does a path that holds a `:` and then an `@` (`https://h/a:b@c` is stored as `https://***:***@c`). When the URL already holds well-formed user info, that user info is redacted and its host kept, unless a `:` and then an `@` follow in the path (`postgres://us@er/x:pass@host/db` is stored as `postgres://***:***@host/db`); so `https://user:token@registry/@scope/pkg` is stored as `https://***:***@registry/@scope/pkg`. An `@` with no `:` before it is a path or query value. Two cases are not fully found: a user name with no password that holds an unescaped `/`, `?` or `#`, and a password that holds an `@` and then a `/` with no `:` after it (`postgres://user:p@ss/word@host/db` is stored as `postgres://***:***@ss/word@host/db`); the redactor cannot tell those forms from an ordinary URL path that contains `@`. - **Milvus Lite enumerates every row**: Milvus Lite 3 answers queries in storage order, so the query iterator's primary-key cursor skipped rows inserted out of key order once a collection outgrew one batch (`scan` above 10,000 rows, native scalar filters, and every `iter_scan`/exact scan above the batch size). - **Atomic upsert**: `upsert(..., atomic=True)` and `upsert_many(..., atomic=True)` commit the entity rows and their Catalog rows through one write call to a backend that claims the new `atomic-upsert` Backend tag, so all of the rows land or none does. On a SQL backend that call is one transaction. Within an existing SQLite transaction, a failed batch rolls back to a savepoint and preserves unrelated writes while the outer transaction remains active. If SQLite rolls back the outer transaction itself, the caller receives the original write error. Other SQL backends claiming atomic upserts roll back the enclosing transaction on a nested batch failure. These backends claim it: `sqlite`, `duckdb`, `postgres`, `supabase`, `mysql`, `seekdb`, `dolt`, `oceanbase`, `mssql`, `oracle`, `pgvector`, `surreal`, `neo4j` and `inmem`. Any other backend refuses `atomic=True` with `ValueError` before the call does anything, as does a plan that spans backends. That includes the generic `sql` type, `clickhouse`, `starrocks`, `trino`, `file`, `json`, `pickle` and the other vector providers, such as Chroma, which sends an upsert larger than its client's batch limit as several calls that each commit on their own. A SQL backend whose engine may commit every statement withdraws its type's claim when it is built. That is SQLAlchemy `isolation_level="AUTOCOMMIT"`, given directly or through `execution_options`; an `autocommit` connect argument, from `params` or `connect_args`, that the driver receives as true in Python (`params` reach pymysql and pymssql as strings, so even `"false"` counts) or, on a driver other than `sqlite3`, as `None`, which leaves the mode to the driver or server default (MySQL's is autocommit); for `sqlite3`, `autocommit=True`, or `isolation_level=None` in its default legacy mode; and a `pragmas` statement that names `autocommit` or `implicit_transactions`, in any case. The tag therefore has a construction layer. The claim relies on the database's transactions. On the MySQL-protocol types that claim it, each table names its own storage engine, so a backend withdraws its claim when it registers a table, keyword-index tables included, whose engine keeps no transactions, such as MyISAM, MEMORY or Aria; `atomic=True` through it then raises `ValueError` until the entity is registered again with a transactional engine. A refused call establishes no Entity from a MetaSchema row. An accepted call registers the Entity class of a definition-shaped MetaSchema row before the write, and a failed write does not undo that registration. For an Entity class that declares a field named `atomic`, the `upsert` keyword stays that field's value, and an atomic write uses `upsert_many(..., atomic=True)`.

It no longer binds the internal MCP entity scope, which on 0.1.2.2 dropped the value and, for a non-None value, failed the write with `PermissionError`. A declared field named `overwrite` passed as a keyword is written too (see the behaviour changes above).

- **Entity-known reads**: `ws.read_rows(entity, object_ids)` and `ws.iter_rows(entity, batch_size=128)` return decoded rows without consulting Catalog; `get`/`get_many` accept `columns=` with `entity=`. `SQLBackend.get_many` selects the named columns in storage, including for third-party backends that inherit it, so an unrequested Vector is neither fetched nor decoded; a requested name that a route does not store is left out of that route's fragments on every provider, SQL included. `columns=` is validated against the entity whatever the ids are: `get_many([], entity=E, columns=[...])` raises exactly as a non-empty call does, and a bare `str` or `bytes` selection raises `TypeError` instead of selecting one field per character. Methods with legacy signatures receive their original arguments. HeavenBase trims their returned fragments before decoding. Projection in storage depends on the backend implementation. `Backend.scan_page(entity_id, after=..., batch_size=..., columns=None)` joins the backend contract as the keyset page primitive; SQL, in-memory, file and Milvus backends implement it natively (a subclass that overrides `scan` or `iter_scan` below that inherited native page uses the portable default) and other providers inherit a portable default over `iter_scan`, which enumerates the route once per page. The in-memory and file backends sort an entity's ids once per change to its id set, not once per page, so a keyset enumeration is linear. With several routes, `iter_rows` reads one keyset page per route for each page it yields and merges them by `object_id`, so rows come in ascending `object_id` order and each row is yielded once, including a row that only a later route holds. When a route orders ids differently from Python, as a case-insensitive SQL collation does, each row is still yielded once while nothing writes during the scan, but the order across routes may not be ascending. A provider's empty page ends the route. Each page uses the current schema. Optional fields added on existing routes may appear on later pages. Start a new scan to include newly added routes. Entity-less bulk reads validate IDs before backend I/O and bound normalized IDs and ambiguity diagnostics by the requested IDs.

- **Opt-in packed SQL vectors**: `vector_packed_type: float64_blob` on a backend, a Database, or `heavenbase.db.providers.<provider>` stores each Vector as a little-endian float64 BLOB instead of JSON text: smaller, faster to decode, and bit-exact. It needs a dialect with dynamically typed columns, marked by the new `database-dynamic-typing` dialect tag; only SQLite claims it. Every other SQL dialect without a native vector type refuses the setting with `ValueError` when the backend, Database or provider config is resolved: on DuckDB and other typed dialects, an existing JSON or TEXT Vector column would store the packed bytes as escaped text, and every read would then fail. A packed SQLite database also reads JSON text, on every supported SQLAlchemy release, so an existing SQLite database keeps reading after opting in (its TEXT column is not retyped; new and rewritten rows are packed). The default is unchanged: SQLite keeps writing JSON text that 0.1.2.2 reads. Packed storage uses eight bytes per component and round-trips all float64 bits. SQLite Core projections distinguish TEXT from BLOB even with a byte-producing text factory or declared-type converter. Direct, precompiled and ORM textual vector statements support byte-producing text factories. Use a Core projection when a converter rewrites the textual vector value. Bulk SQLite lookups can select JSON-text and packed vectors without adding bind parameters. HeavenBase 0.1.2.2 can silently return an incorrect vector when the packed bytes form a valid JSON array. The 0.1.2.3 JSON-text reader raises `ValueError` for packed rows. Enable packed storage only when every reader uses `float64_blob`. Packed rows are kept in that format. `default.yaml` shows the switch, commented out, under `db.providers.sqlite`. A workspace that is already registered opts in through `heavenbase.db.providers.sqlite.vector_packed_type`: its backend definitions are its construction contract, so adding the key to a backend definition is refused with `FileExistsError`.

- **SQL reads run outside the backend lock**: `SQLBackend.scan`, `scan_page`, `get_many`, `exists_many`, `count`, and `execute` take the backend lock only to plan (resolve the live `Database`, the entity's table and side-table specs, and the cached statement) and run the statement and decode its rows outside it, so reader threads overlap on the engine's connection pool instead of queueing behind each other. Mutations, `ensure`, `drop`, workspace rebinding, and strategy-adapter query execution keep the lock for the whole call, so a read still waits for a mutation in progress; `drop` waits up to 30 seconds for the reads running outside the lock before it removes the database, then proceeds (0.1.2.2 waited for a running read without a limit); a read that would run after that, including one planned before the drop, raises `RuntimeError` ("unavailable after drop") instead of a `DatabaseError` from the disposed engine, and so does a read still running then if it fails (one that succeeds returns its result); `get_many` and `exists_many` over more ids than one batch run their batches under the lock, as in 0.1.2.2; and a read keeps the lock across its statement on an engine that cannot serve two threads at once (`pool_class: static`, `assertion` or `singleton`, or any in-memory database, whose second connection would be a separate empty database). Such an engine is private to its `Database` facade, so two backends on one database each get their own engine and one backend lock covers every statement on it. A backend that does not claim the `atomic-upsert` tag keeps the lock across its reads too: the generic `sql` type, `clickhouse`, `starrocks`, `trino`, a type the Registry does not know, or a backend whose engine may commit every statement (see Atomic upsert). Such a backend does not promise that its upsert, a delete followed by an insert, is one transaction: ClickHouse runs them as separate statements, an engine that commits every statement commits each of them on its own, and on the others the upsert's transaction is only as atomic as the dialect and its storage make it. A read outside the lock could run between the two. Reads also keep the lock at `READ UNCOMMITTED` and on SQL Server unless the session uses `SNAPSHOT`, or `READ COMMITTED` with `READ_COMMITTED_SNAPSHOT` enabled. MySQL, MariaDB, SQL Server and SQLite probe the connection’s session isolation level. If the probe fails, the configured isolation level is used where available. On a bounded queue pool, lock-free reads use the slots left after reserving one per participating backend and accounting for other engine users. They wait for a slot, or take the backend lock when there are no read slots. A call made while holding that backend lock stays under it. If direct engine use checks out a reserved connection after reads filled the other slots, a backend lock holder can still time out. Size the pool through the backend map's `pool` mapping (`pool_class`, `pool_size`, `max_overflow`, `pool_timeout`, `pool_pre_ping`, `pool_recycle`, `connect_args`); the defaults are unchanged.

- **Batched SQL lookups and drops under reads.** `get_many` and `exists_many` over more ids than one batch (a batch holds at most `heavenbase.backend_defaults.sql.id_lookup.batch_size` ids, 500 by default) again see a write of the same backend whole or not at all; an earlier 0.1.2.3 change ran their batches outside the backend lock, so a write could land between two batches. A SQL backend `drop` (also `pgvector` with `shared_database`, `clickhouse`, `starrocks` and `supabase`) again waits for the reads running outside the backend lock before it removes the database: it waits up to 30 seconds, then proceeds (0.1.2.2 waited without a limit), and a later read of the dropped database raises `RuntimeError` ("unavailable after drop"), as does a read still running then if it fails (one that succeeds returns its result); an earlier 0.1.2.3 change let a running read fail with `DatabaseError`.

- **`NetworkProxy` holds are tracked per process**: `Database` enters its proxy scope on every engine access, and unlocked SQL reads now do so concurrently. `LLM` chat, embedding and image calls each enter their own instance, so concurrent async calls overlap. The holds of every instance are now tracked together under one process-wide reentrant lock. Each hold applies its settings and records the environment it found, so the newest hold's values are live while holds overlap. The newest hold restores what it found when it exits, as before. An older hold that exits first hands what it found to the newer holds. The original proxy environment therefore returns after the last hold exits, whatever the exit order. In 0.1.2.2, concurrent `LLM.achat` calls with `http_proxy` could leave the variable set for the rest of the process. Calls to the default ollama, lmstudio and omlx providers, which set an empty proxy, could also erase the user's own proxy. Concurrent readers of one `Database` no longer fail with `dictionary changed size during iteration`. As in 0.1.2.2, only an empty-string setting clears a variable. A setting that is not a string raises at enter and leaves the environment as it was. An instance with no settings changes nothing. A garbage-collection finalizer or signal handler can exit a hold on the thread that is inside another proxy operation. An exit of a hold that predates the interrupted section waits until the section finishes. A hold entered and exited inside the interrupting call applies and restores its settings immediately. A child process forked while another thread held the lock starts with it free. Overlapping exits of the same instance claim distinct holds. Interrupted enters and exits release the lock and attempt recovery up to three times before propagating the first exception. An interruption at the start of an exit can prevent it from claiming a hold. On Python 3.10, a second interruption during exception propagation can also prevent lock release. During interpreter shutdown, a proxy operation skips its critical section if the lock is held by another thread. Overlapping holds share the process environment, as in 0.1.2.2, so the newest hold supplies the values every thread reads. Holding a lock for the entire call would be unsafe because a caller can suspend one stream and advance another before resuming it. Set one shared route for overlapping calls, or run calls with different proxy settings in separate processes.

- **SQL statement rendering and reuse**: `Database` execution no longer renders SELECT, DML or DDL constructs on the success path at `readonly=False`. After a statement runs, it is classified from the SQL the driver ran. With `readonly=True` or `None`, a SELECT construct is rendered once before it runs, with the database's own dialect, when its structure cannot show what it renders. That covers an ORM statement; a SELECT nesting SQL rendered verbatim that might write (`text()`, a literal column, an `extract()` field, a collation, a prefix, suffix or hint, a custom `.op()` operator, or a name declared `quote=False`); and a SELECT holding an element class or `CAST` type defined outside SQLAlchemy or overridden with `@compiles`, or a type that wraps binds or columns in its own SQL. A `text().columns()` construct is classified by its own text. `SQLBackend` reuses one construct per entity and statement shape (bounded to 512 per backend with least-recently-used eviction, page sizes and cursors bound as parameters), so repeated lookups, scans and writes hit SQLAlchemy's compiled cache.

- **Chroma never computes embeddings**: every Chroma upsert now passes explicit embeddings. In 0.1.2.2 a batch with any row lacking a vector carried none, so Chroma embedded the documents with its default ONNX model. That meant a model download on first use and a failure offline. For a vector entity it also meant a dimension error, or a stored vector replaced by the model's embedding. A row that omits its vector now keeps the stored vector. An entity with no Vector field on Chroma, including one whose vector is stored on another backend, stores a constant placeholder embedding. Its width matches the collection, so collections written by 0.1.2.2 stay writable. Rows read from Chroma no longer carry a vector that is stored on another backend.

- **Chroma scans in one linear pass**: `ChromaBackend.iter_scan` paged with `get(limit=..., offset=...)`, and a Chroma page slows down as its offset grows, so one pass over N rows was quadratic. An exact `near(..., exact=True)` on a Chroma route, which streams one such pass, spent minutes on 200,000 rows. `iter_scan` now lists the collection's ids once and fetches rows by id one page at a time, so a pass is linear and returns rows in the same order. A row deleted during a scan no longer makes it skip a live row it had not reached. `ws.iter_rows` on a Chroma route still re-enumerates the route for every page, so it stays O(N²/batch_size).

- **Chroma reads above SQLite's variable limit**: Chroma binds SQL variables per id, per match and per `in` value (one per string or bool, two per number), and the SQLite limit depends on the build and connection. A common default is 32,766 per statement. `scan`, `get_many`/`exists_many` of more ids, a native metadata filter that matched more rows or whose `in` lists bound more variables (more than about 16,380 numbers, or two lists together), and a native `near` with a larger `top_k` or such a filter all failed with `too many SQL variables`, as they did in 0.1.2.2. Rows are now read by ID, at most 4,096 IDs per request. A native filter is reapplied when fetching listed IDs or the hits of a large near. The fetch size accounts for the filter's bound values and clause overhead. For near requests above 4,096 neighbors, HeavenBase selects candidate IDs, fetches their rows, and scores and ranks them using the embeddings it returns. A filter above the limit is read natively per `and`/`or` operand and per run of `in` values, and the returned rows are checked again with the filter's row predicate in Chroma's order. A `near` with such a filter ranks those matches by the collection's own distance space, with the score a native query reports. These filters stay native, and `explain` reports them as native. With chromadb 1.5.9, a single local get succeeded with 32,763 ids and failed with 32,764.

- **Chroma upserts above the client's batch limit**: an upsert of more rows than the Chroma client's `get_max_batch_size()` (5,461 on the local clients of chromadb 1.5.9) failed with `Batch size of N is greater than max batch size`, as in 0.1.2.2. It now goes to Chroma as consecutive calls of at most that many rows, in order. Each call commits on its own, so a provider error in a later call leaves the earlier calls applied; a missing vector is still caught before anything is written. Rows upserted without their vector read the stored vectors in bounded `get` calls, so more than 32,763 of them no longer fail with `too many SQL variables`.

- **Missing-value filters on numeric and Json fields**: `field == None`, `field != None`, `{field: None}`, `$ne: None` and `$in` with `None` test for a missing value on Integer, Float, Duration and Json fields too, as they did on text, Boolean, Date and Array fields; 0.1.2.2 raised `TypeError` or `ValueError` for them there. Chroma, Pinecone and Elasticsearch send such an operand to the portable scan instead of a native filter that cannot carry null; on Chroma every such filter failed in 0.1.2.2. LanceDB filters compile `IS NULL` and `IS NOT NULL` for such an operand and keep a row without the field in `$ne`, as every other backend does; before, these filters matched no row there, and `$ne` with a value dropped rows without the field. Chroma and Pinecone compile empty membership lists for portable filtering too. Pinecone needs a route that can supply the candidate rows when the provider cannot apply the filter.

- **Smaller fixes**: `LLMCache.reset(drop=True)` drops the selected stores under the Context lock. The hidden stores of any Context on the dropped storage reopen on fresh storage (see **Hidden storage after a drop**), and independent caches keep their rows. Cache subclasses may define equality without hashing. Untraced streaming, async tool-stream fallback and compaction preserve legacy LLM override signatures. A non-exact `near` evaluated together with its filter (`near_filter_mode: "combined_scan"`) carries the filter's result metadata, such as the `match` of `contained_in`, which 0.1.2.2 dropped; an empty result still declares it, so `select("match")` returns `[]`. A backend `get_many(..., columns=...)` given a name that is not a string raises `TypeError` before the provider read on Pinecone, Chroma, Milvus, Elasticsearch, OpenSearch, MongoDB and TinyDB; Pinecone no longer drops its client on that error, and no backend records it as `client_error`. A write flag given a non-builtin bool, such as NumPy's `np.True_`, is refused with a message that names the type with its module (`numpy.bool` on NumPy 2, `numpy.bool_` on NumPy 1). A `DashboardAPI` subclass that overrides `assist` or `assist_stream` with the 0.1.2.2 parameters keeps working: a request field the client left unset is passed only to a method that accepts it, and a field the client set that the method cannot take gives HTTP 400 on both routes. Merging LLM usage (multi-call results, batches and the CLI usage line), an agent `Session`'s usage and a streamed assistant turn's usage no longer raises `TypeError` when a provider reports a count as null and a later usage reports a number for the same key; the number replaces the null. `total_tokens` is derived only when both the prompt and completion counts are numbers (see **Usage totals**). This also failed in 0.1.2.2, except for the streamed assistant turn, whose merge is new. The Anthropic routes' own usage normalization had the same null-count `TypeError`; see **Anthropic stream usage**. A Capsule registry call made while the Context lock is held, such as from a compute hook inside a workspace write, no longer deadlocks with another thread that builds the Context's registry facade on its first use or after `reset_capsule_registry()`: that build took the Context lock while holding the process-wide registry lock. A facade whose build was running when a reset started serves only the call that built it and is not cached. Also in 0.1.2.2. Workspace construction, including each LLM cache or Capsule registry open and each rebuild after a drop, no longer rereads the packaged module folders, reseeds the package's own handlers, or rebuilds the MetaSchema registry rows after every entity registration. A process keeps these while their inputs are unchanged: a folder's stat fingerprint (on Windows also the bytes of the descriptor and module files), and the module catalog's publication. A zip-imported package, or a folder with a file changed in the last two seconds, is read on every setup. Every module setup still compares the module-set marker with the Context's Registry, and `ModuleService.setup(force=True)` reads every folder again. Handler contributions installed by anyone else are still seeded for each new workspace, with the configuration in effect then; a package contribution that comes after one of them in priority order is too. A resolver other than the Context's `ModuleService` is seeded and its storage profiles are read at every call. `registered_storage_profiles()` and `storage_profile_for()` return copies, and editing the object that `StorageProfile.register()` returns no longer changes later placement: register the changed profile. A Context keeps a template of the package's seeding: a Context with one workspace uses about 5 MiB more than in 0.1.2.2 (20.4 against 15.1 MiB with an in-memory workspace), and each further workspace uses less (6.3 against 10.8 MiB in memory, 3.1 against 5.6 MiB on SQLite). On Python 3.12 a rebuild after a drop takes about 1 s instead of 3.6 s, and a later workspace construction in a process about 1.5 s of CPU instead of 4.6 s (medians on one server). On Windows, capturing a module folder retries its final rename for about six seconds when another program, such as a virus scanner or indexer, briefly holds a handle (WinError 5 or 32), instead of failing with `PermissionError`. Removing the capture's temporary folder retries WinError 5, 32 and 145 the same way. A removal that still fails, on any platform, only logs a warning and leaves the `.capture-*` folder in the store: it no longer fails a capture that succeeded, or replaces the error of one that failed. Also in 0.1.2.2.

- **Batch upserts whose rows set different fields**: on SQL backends, an `upsert_many` batch whose rows omit different optional fields now stores each row as given. Before, if an earlier row held a field that a later row omitted, the batch failed with `A value is required for bind parameter`; for a field routed to a second backend, the main rows were then already written without the routed value. If an earlier row omitted a field that a later row held, that later row's value was silently not stored. This was also present in 0.1.2.2.

- **DuckDB commits statements whose response is dropped**: on DuckDB, whose driver reports rows for every statement, a statement run outside a transaction whose response was dropped was never committed. This covered DDL, DML, `COPY ... FROM`, `COMMENT ON`, `WITH ... INSERT` and a write that follows a leading `SELECT` in multi-statement text. As a result `Database.add_table_col` never added a column, and an entity with a `SideTable` field could not be written (`Binder Error: ... does not have a column with name "_present_<field>"`). This was also present in 0.1.2.2.

- **Rollback of failed standalone statements**: outside `db.tx()`, a `Database.execute` or `orm_execute` call that fails is rolled back before it raises, or before it returns its error with `safe=True`. In 0.1.2.2 the failure path committed whatever the statement had done, so an executemany whose later parameter set failed (a duplicate key, for example) kept the earlier sets on drivers such as `sqlite3`, while the same call inside `db.tx()` rolled them back. An engine that commits every statement has already committed the parameter sets that ran before the failure, inside `db.tx()` or not.

- **Registering a workspace after another process wrote the registry**: `WorkspaceSpec.register`, which constructing a tracked workspace calls, reads the workspace registry again and recomputes the update when another Context or process published the registry after this Context read it, instead of raising `RegistryConflictError`. This was also present in 0.1.2.2, and it now matters more, because a schema change of a manifest-backed workspace publishes the registry (see Reopening a workspace by id below).

- **Shared sparse-GRAM index**: workspaces that resolve the same SQL entity table share its rows. Earlier releases kept separate keyword indexes per workspace. A write through one workspace left every other workspace's index stale, so `contained_in` returned rows whose keywords had changed and missed rows that matched, and a second workspace that indexed the same object and keyword failed with `UNIQUE constraint failed: hb_gram_keywords.keyword_id`. Workspaces resolving the same sparse-GRAM tables share one index per entity field. Keyword IDs include the index namespace. An indexed `contained_in` lookup sends three statements more than 0.1.2.2: the fingerprint before and after the lookup, and the indexed keyword lengths. On 1,000 rows a lookup without a match took about 1.3 times as long on SQLite and 1.5 times on PostgreSQL 16 and MySQL 8.4 (Catalog lookups 1.2 to 1.7 times); with matches 0.9 to 1.2 times. The index's stored fingerprint is checked again before and after every `contained_in` lookup and, inside the write's transaction, before each write that stores indexed rows, so a backend whose options or `gram` option no longer match it raises instead of missing rows (see the behaviour changes). A rebuild deletes the old index rows before it reads the stored rows. A registration that changes an entity's stored fingerprints, and only such a registration, first waits for the entity's writes in progress and holds off new ones until it commits. It takes a `SHARE` lock on the entity table on the `postgres`, `pgvector` and `oracle` types, shared locks on its rows on the `mysql` type, the write lock on `sqlite`, and a gate in the process on `duckdb`, whose files only one process writes at a time. A reopen with unchanged fingerprints takes no lock. On those types a write either commits before the rebuild reads the stored rows, or is checked against the new index, so no write commits rows indexed with the earlier options and no write makes a rebuild fail. That holds at every isolation level of the write on `postgres`, `pgvector` and `mysql`, with the two exceptions below (a PostgreSQL login without the `UPDATE` right and a MySQL write at `READ COMMITTED`): a write in a `REPEATABLE READ` or `SERIALIZABLE` transaction that began reading before the change committed fails, because its snapshot cannot show the change; roll the transaction back and run it again. On PostgreSQL that is the serialization failure of the row statement (`DatabaseError`, SQLSTATE 40001); a write that finds index tables its snapshot lacks raises `SparseGramIndexConflictError` on PostgreSQL and MySQL. On PostgreSQL the registering engine has to run at `READ COMMITTED`, the default: the index a registration builds at `REPEATABLE READ` or `SERIALIZABLE` misses a row that a write commits after the registration's first read. On `mysql`, a write at `READ COMMITTED` that reaches the server after the registration that first indexes its entity locked the rows, and before that registration stored the entity's first epoch, is not refused, and its row is missing from that index. A PostgreSQL registration gives every entity of a database that holds the index tables an epoch row for this. The check locks that row, which takes the `UPDATE` right on `hb_gram_meta`; for a login that may not update its `value` column the check reads plainly and holds at `READ COMMITTED` only. HeavenBase asks for that right once per backend connection, so reopen the workspace after granting or revoking it. Registrations need no `UPDATE` right on `hb_gram_meta` on PostgreSQL and MySQL-protocol servers; on Oracle and SQL Server a registration that adds an index still sends an `UPDATE`. Opening keyword storage that 0.1.2.2 made adds an index on keyword length to `hb_gram_keywords`; where the server refuses it, lookups read without it. A keyword table in a DuckDB file that has held rows does not get it, and lookups there read without it. On `oracle` it holds at the default `READ COMMITTED`; at `SERIALIZABLE` only a write of keyword rows the registration rebuilt fails (`DatabaseError`, ORA-08177), and a write of an entity another workspace started to index meanwhile is not refused and its rows are missing from that index. On `duckdb`, a transaction that ran any statement, even one reading no table, before it reached a write or index change while the other side changed the entity is refused with `SparseGramIndexConflictError`, because it reads from a snapshot taken at its first read; roll it back and try again. The `dolt`, `seekdb` and `oceanbase` types take no such lock, because their servers have no lock that writers can hold together while a registration waits for them: dolt takes no locks, and seekdb and OceanBase have only exclusive row locks (`LOCK IN SHARE MODE` among them) and no gap or table locks. Nor do `mssql`, whose lock has not been run against a SQL Server, and the generic `sql` type. There, a write that checked the fingerprint before another process's rebuild committed can still commit rows indexed with the earlier options, and a write that commits while a rebuild reads the stored rows can make the rebuild fail with a unique-key error. Closing that gap with the locks those servers have would serialize every write to the entity. This is a limit of the shared index introduced in 0.1.2.3; in 0.1.2.2 the separate per-workspace indexes could already go stale. Register every backend with the same options, pause writers while index options change, and register again, with writers paused, after such an error.
 Every registration of a field looks for per-workspace indexes that 0.1.2.2 wrote for it on the database, through any workspace id. When one workspace wrote such an index, this version rebuilds the shared index from stored rows, then deletes that index and leaves a marker in its place, in the rebuild transaction during SQL schema publication. The marker makes 0.1.2.2 opening that workspace again rebuild its own index from stored rows. When two or more workspaces wrote such indexes, they are kept as they are: 0.1.2.2 computed keyword ids without the workspace, so two of its indexes could not both hold every row, and rebuilding both would stop the second workspace from opening. 0.1.2.2 then opens each workspace with the index it had, which misses rows written through other workspaces and through this version, as it did in 0.1.2.2. A workspace whose index this version had already retired, before a second workspace wrote one, opens in 0.1.2.2 with an empty index for that field. With multiple retained 0.1.2.2 indexes, a fresh registration or registration with `allow_replace=True` rebuilds the shared index from stored rows, including after a legacy rewrite restores the same keyword IDs. A repeat registration on a live workspace reuses the live registration. PostgreSQL serializes registrations per entity and metadata table. SQL routes of one entity that share a database share one publication transaction and write each row once (see **SQL routes that share a database**). Registering `SparseGramIndex` fields through PostgreSQL routes whose login role, current role or search path differ while they resolve the same index tables raises `ValueError`.' A 0.1.2.2 process that stays open while this version writes to the same database is not supported. Short keyword widths are read on every query, so a keyword of a new width indexed through another backend instance or process is found; this was also missed in 0.1.2.2. When no legacy index exists, the first workspace to register a field leaves a single marker so 0.1.2.2 can rebuild when reopened through that workspace. Other workspaces without a legacy index can reopen with an empty one. A lookup reads short keyword widths in one query. SQL rechecks the whole filter and constructs match metadata from the keywords in the returned row, including in negated trees. Combined and exact SQL near scans generate short-width hashes from their registered options, so they continue matching after a peer rebuilds or retires the index. Rows deleted before hydration are omitted (see **Query rows deleted before hydration**). Token and space modes verify whole units in the full normalized query, including when hashes collide or a tokenizer depends on query context. When literal alignment is unavailable, verification tokenizes the query through both ends of the span and checks that removing it preserves the surrounding tokens. Verification reuses query hashes across equivalent keyword widths.

- **Reopening a workspace by id keeps later schema changes**: reopening a manifest-backed workspace by id (`HeavenBase(id)`, `HeavenBase.load(id)`, `WorkspaceSpec.open_detached()`) no longer undoes a later schema change. The saved replay manifest kept the import's definitions. After `alter_entity` or `register(..., allow_replace=True)` added a field, the reopened workspace dropped the field and re-published the old structure to MetaSchema, and the next write of a row stored NULL in that column. Now, when the tracked workspace changes an entity its saved manifest defines (by `entity_id`, or by the `name` it is derived from) through `register`, `alter_entity` or `describe`, the saved definition is replaced with the live one as `to_manifest()` exports it. The workspace registry is re-read before the write, and the write is repeated after a concurrent update, so another process or Context keeps its changes to other entities. Entities registered after the import are not added. The saved definition is left unchanged, with a `UserWarning`, in three cases. One is a change made through a detached or untracked facade built from the same construction (the same backend configuration, written the same way), including the first registration of the entity on a detached facade that did not replay the saved manifest (`HeavenBase(id, detached=True, backends=...)`) when it differs from the saved definition. A first registration is compared with the workspace registry as its Context last read it, so a manifest another process or Context imported after that is not seen and no warning is emitted. Another is a change made through a facade whose definition of the entity is out of date, because another process or Context saved a different one since; that one is kept. `HeavenBase.load(id)` in the same Context returns that facade, so release it before reopening and making the change again. The third is a live definition that could not be replayed (a value that is not JSON, such as a `decimal.Decimal` or tuple default or a date inside a Json default, or a compute hook that is not registered as a module); its `catalog` and `gram` options are still saved, so reopening by id does not raise. `to_manifest()` and the saved manifest write a `datetime.date` or `datetime.datetime` default or example as its `isoformat()` text with its type (`default_type`, `example_types`); import, reopening and `Entity.from_schema` restore the value. A tracked import of a definition that holds such a value raised `TypeError` in 0.1.2.2, after its definitions were registered. No warning is emitted when the saved definition already replays to the live one, as when two processes make the same change; a saved definition naming a hook from the `computes=` mapping given to the facade is compared through that mapping. A manifest saved by an earlier release is refreshed the next time such a change is made. This was also present in 0.1.2.2. The saved manifest holds no extension entity definitions (see **Manifests and extension entities**).

- **Extension entities keep their extension's definition**: an enabled extension registers its own definition of each of its entities (such as `memory-note`, `agent-session`, or an entity its setup hook returns) every time the workspace opens. In 0.1.2.2 a later `alter_entity`, `describe` or `register(..., allow_replace=True)` change to such an entity was silently undone on reopen, and values written to a field it added could no longer be read. These calls now raise `ValueError` when they would change the entity's structure, `catalog` or `gram` option, or metadata (name, descriptions, tags and examples), with or without `allow_replace=True`. A call that changes nothing (the same definition again, including the mapping `to_manifest(include_system=True)` exports for an entity with derive or compute hooks such as `agent-message` or `db-table`, or `describe` with the current values) is accepted and leaves the extension's class registered; 0.1.2.2 raised `ValueError: Derive target 'catalog.desc' needs compute` or a `KeyError` for such a mapping. This includes the extension's own class loaded in a Context with another root, such as the public `hb.Message` and `hb.Session` facades used with a workspace whose Context has its own root, as 0.1.2.2 accepted: `register()` and `alter_entity()` compare compute and derive references relative to the extension's content-addressed package, as manifest import does. A definition mapping for an extension entity that differs and cannot be compiled raises the extension's `ValueError`. Keep extra fields in a separate entity. An extension owns its entity definitions. Store workspace-specific fields or metadata in a separate user entity keyed by `object_id`. Change the extension itself when the definition should apply to all its workspaces.

- **Manifests and extension entities**: importing a manifest, or reopening a workspace by id from its saved manifest, skips an extension entity's definition when it has the extension's structure and options; its name, descriptions, tags and examples are not applied, and a `UserWarning` names those the definition states differently, whether or not the entity has derive or compute hooks (0.1.2.2 applied the descriptions, tags and examples and already kept the extension's name). Compute and derive references into extension code are compared without the package name the code is loaded under, which differs per HOME and Context root. So a manifest exported with `include_system=True` from a workspace with the agent extension now imports, also on another machine and when 0.1.2.2 exported it (0.1.2.2 raised `ValueError: Derive target 'catalog.desc' needs compute` even in the same HOME). A definition with another structure or `catalog`/`gram` option raises `ValueError`, also with `allow_replace=True`, before the import registers any of the manifest's definitions, and the import writes no `WorkspaceSpec`. The manifest a tracked import saves for reopening by id no longer holds extension entity definitions. In 0.1.2.2, descriptions, tags and examples from a manifest could change the extension class shared by all workspaces in the Context, and the changes disappeared on reopen. A workspace-specific overlay needs an independent class and persistent metadata.

- **MCP `define_entity` registration options**: `define_entity` registers the definition it is given through `workspace.register`, so the `catalog` and `gram` options a definition states apply to a new entity and, with `replace=True`, to a replaced one. Before, a new entity always got `catalog="full"` and `gram=True`, `replace=True` kept the old options, and a later Python `register` of the same definition failed with "already registered with catalog='full' and gram=True". Before, `describe_entity` listed it, and the query then failed with a `LookupError` naming `gram=False`. The query compiler and `describe_entity` now apply the same rule. Registration options are new in 0.1.2.3.

A differing definition gets register's extension error. This also failed in 0.1.2.2.

- **`redact_url` keeps the host as written**: when it redacts user info, IPv6 brackets and host case survive in redacted database URIs, LLM config URLs and trace options. 0.1.2.2 lower-cased the host and dropped the brackets.

Stored descriptors hold only digests, so no stored path changes. Other platforms are unchanged.

The bundled UI works with a subclass using the 0.1.2.2 signature, and that override receives no session identifiers. Other request fields are passed normally. - **Identity Catalog rewrites clear stale keyword rows**: a merge-mode identity write of an existing Catalog row maintains the keyword index in the same transaction, even if a direct or full-mode writer changed the row after the lookup. An identity write that finds no row, or uses fresh mode, writes no keyword rows, but after its row statements, in the same transaction, deletes any that another writer committed for that Catalog row (one read per call). `ws.audit()` lists Catalog keys whose sparse-GRAM rows differ from what their stored row indexes under `stale_keywords`, and `ws.repair()` writes those rows again (`stale_keywords_rewritten`). The audit reads every Catalog row in its scope again with its keyword and posting rows: on a `full` Catalog of 4,000 rows with three keywords each it took 2.6 to 2.9 times as long.'

- **Retiring sparse-GRAM fields**: registration retires the keyword index of a field that is removed, retyped or otherwise unbound. Binding it again checks the fingerprint and rebuilds from stored rows when needed.

- **Recovering a failed replacement registration**: after a failed `register(..., allow_replace=True)`, HeavenBase re-establishes the previous registration on the backends it ensured, including scalar and unique indexes the replacement dropped (on DuckDB no index is dropped, so one that the failed attempt created stays). On SQLite, in-memory and file storage (`json`, `pickle`), rollback restores MetaSchema rows that still hold the failed attempt's values and preserves later edits or deletions. On other storage, such as DuckDB or a server database, no restore is done: the rows the failed attempt wrote stay. A failed or unsupported restore emits `RuntimeWarning`. Independently committed index changes can survive a later failure. Every SQL backend, pgvector and StarRocks included, adds a column to the table it caches only once the database has added it, and a failed registration leaves no table or side-table spec it introduced in that cache. A replacement whose column the database rejects, such as a required field added to a table that already holds rows, therefore leaves the entity readable and writable through the same facade with its previous registration, and registering the previous definition again works. Before, every read and write of the entity selected the missing column until a new facade was opened, and registering again repeated the failed `ALTER TABLE`; this was also present in 0.1.2.2. StarRocks ensures its table through the same path as the other SQL backends: a registration adds the column of each field the stored table lacks (`ALTER TABLE ... ADD COLUMN`), caches a column only once the table holds it, and creates the table again if an earlier `CREATE TABLE` failed. Before, also in 0.1.2.2, a replacement that added a field never added its column, so on the same facade every write silently dropped the field's value, and a new facade over a table an earlier registration created selected a column the table lacked, so every read and write of the entity failed. A new StarRocks table holds the fields routed to StarRocks (0.1.2.2 declared a column for every field of the entity) and keeps `SideTable` fields inline as before. On pgvector, a replacement registration that adds a field now adds its column; before, it failed with `KeyError` (also in 0.1.2.2). A scalar or unique index whose build fails is no longer kept on the backend's cached table, as a column the database rejects is not, so the previous registration is re-established and registering again with `allow_replace=True` works. Before, also in 0.1.2.2, a unique index the stored rows rejected (for example a duplicate another writer stored after the duplicate check) stayed declared, so re-establishing the previous registration failed and every later registration of the entity tried to build it again until a new facade was opened.

- **Scalar indexes on repeat registrations**: a SQL registration builds only the scalar indexes its resolved plan asks for. A field declared `.index(enabled=False)` was indexed and then dropped again on every registration, a full index build at each process start that, on PostgreSQL, blocks writes while it runs. This was also present in 0.1.2.2 on every SQL backend type except `pgvector`.

- **Scalar indexes on DuckDB**: HeavenBase reads a DuckDB table's indexes from `duckdb_indexes()`, because SQLAlchemy's DuckDB inspector reports none. On DuckDB 0.10 and later, the lookup handles columns that DuckDB quotes, such as `name`, `order`, `group`, `user` or `limit`. Before DuckDB 1.1 it reads the columns from the index's `CREATE INDEX` statement, and it leaves expression indexes out. No registration drops an index on DuckDB, as in 0.1.2.2, because DuckDB 1.5.3 cannot replay a write-ahead log that drops indexes and then writes rows: a process that ended without a checkpoint would leave a file that no process can open. A unique constraint removed from a field, or a removed field's, therefore keeps refusing duplicates on DuckDB, and a field declared `.index(enabled=False)` keeps the default index it had; a repeat registration with the same definition sends no `CREATE INDEX`. Before, also in 0.1.2.2, every registration there sent `CREATE INDEX` again. For a like reason a table of a DuckDB file that has held rows gets no index with a column that none of its indexes covers, whether the field is new or was not indexed before: reads scan for it, and later registrations do not add it. A registration that declares a unique constraint with such a column, such as one on a `Timestamp` field or on a field whose default index was left out, raises `ValueError` before it changes the table. An index or a unique constraint over columns that are all indexed already is created. Declare such a constraint before the first row is stored, or store the rows in a new database registered with it. An in-memory DuckDB database and tables that have held no rows are not affected. The rule leaves existing indexes in place, so it does not repair a file that later processes already cannot write, and it does not see a first row that another connection writes while an index is being created. A database dialect can supply the new `index_reflection_sql` template for this lookup.

- **Which scalar indexes a SQL registration drops**: on SQL backends other than DuckDB, a registration drops only indexes named as HeavenBase names an index on their columns, only when this route's table declares all of those columns, and none that the plan asks for on any of its routes. A field removed in the workspace object that declared it therefore loses its index and its unique constraint; one that a new process registers without keeps them, with or without `allow_replace=True`, as in 0.1.2.2. Two routes of one database keep each other's indexes, and a definition that lacks a field leaves another workspace's index on it in place, unless the same workspace object registered the field before. A composite index that also covers a field the route does not declare is kept, where 0.1.2.2 dropped it. When a field moves to a route on another database, the old database keeps the field's indexes, the unique one included; HeavenBase no longer writes the field there. A replica that gave up the ownership of a unique constraint keeps its unique index as well, and can refuse a write while its rows lag behind the owner; the new owner keeps its redundant plain index beside the unique one.

- **DuckDB indexes and primary keys in ingest and reflection**: the database analyst extension now reads a table's indexes through the `Database` catalog reflection, so a DuckDB source is ingested with its indexes; it read them from SQLAlchemy, which reports none on DuckDB. `Database.pks()` uses the dialect's `primary_key_reflection_sql` when SQLAlchemy reports no primary key, as its DuckDB inspector does from DuckDB 0.9 on; on DuckDB it reads the PRIMARY KEY constraint from `duckdb_constraints()`, so a composite key keeps its declared column order, and the ingest marks DuckDB primary-key columns again. `Database.schemas()` returns each schema once: duckdb-engine lists a DuckDB 0.10 schema once per attached database, and the ingest refused such a source with a duplicate `db-table` object_id. These were also present in 0.1.2.2. The DuckDB index lookup also accepts the `<database>.<schema>` names that `Database.schemas()` returns from DuckDB 0.7 on, and it runs on DuckDB 0.5 and 0.6, whose index catalog has no `database_name` column.

- **Index reflection on DuckDB, seekdb and OceanBase** (also in 0.1.2.2): `Database.index_column_sets` counts a DuckDB table's primary key, and a MySQL-protocol table for which SQLAlchemy reports no index, as on seekdb and OceanBase, is read from `information_schema.STATISTICS`, so `create_missing_indexes` no longer fails with `Duplicate key name` on a second ensure.

- **Row replacement on DuckDB before 1.2**: DuckDB before 1.2 keeps a deleted key in its indexes until the deleting transaction commits. In that transaction it rejects inserting the key again and updating an indexed column of the row (`ON CONFLICT DO UPDATE` is refused for an indexed column and `INSERT OR REPLACE` keeps its old value), and every SQL row replacement deletes and inserts in one transaction. Replacing a stored row therefore failed with DuckDB's duplicate-key error, and a workspace whose main route was DuckDB before 1.2 failed at bootstrap with a duplicate primary key for `entity:sys-metaschema`. On such a release a `duckdb` backend, or a `sql` backend whose database is DuckDB, now refuses a write that would replace a stored row, and a sparse-GRAM rebuild or metadata change that would replace stored index rows, with a `RuntimeError` naming the 1.2 requirement before running it; the write rolls back. Inside a transaction that spans several write calls, a row that an earlier call inserted counts as stored. Connecting, inserting new rows, deleting and reading work as before. The package declares no DuckDB bound and the locked version is 1.5.3. This was also present in 0.1.2.2. Use DuckDB 1.2 or later for replacements or index changes that replace stored rows.

- **Default index after a unique constraint is removed**: a field whose `.unique()` a registration removes gets its default non-unique index in that same registration, on every SQL backend except DuckDB, where the unique index stays. Before, also in 0.1.2.2, the field had no index at all until the entity was registered again.

- **Keyword-index checks on writes**: every SQL write checks that no keyword index the route does not maintain covers the entity, through every route, also `pgvector`, `starrocks` and engines that may commit every statement. A writer whose definition leaves out or does not index a field that another workspace indexes is refused instead of leaving that index stale, also when the index was created after the writer registered, except on an `oracle` engine at `SERIALIZABLE` for a write whose transaction began before another workspace started indexing the entity, and on a `mysql` engine at `READ COMMITTED` for a write that meets the first index of its entity (see **Shared sparse-GRAM index**). The adapter keeps the index state it last read for each entity: whether the index tables exist, the entity's fingerprints, and an epoch that every change of those fingerprints replaces in the same transaction. On the `sqlite`, `duckdb`, `postgres`, `pgvector`, `mysql`, `dolt`, `seekdb`, `oceanbase` and `oracle` types, on a route that claims **Atomic upsert**, the first `DELETE` or `INSERT ... SELECT` (on Oracle a conditional `INSERT ALL`) of each table in a write carries a condition that holds only while that state is unchanged, so a write sends no query of its own for the check. Five single upserts of a plain entity on `postgres` send 10 statements, as in 0.1.2.2. A `DELETE` that removes any row confirms the state; when a table's `DELETE` removes none of the rows it names, the call inserts its first row into that table on its own. A call that inserts more than one new row into such a table therefore sends one statement more than 0.1.2.2 for that table, the Catalog table included: a workspace `upsert_many` of several new rows of an entity with Catalog rows sends two more. When the state has changed, the write reads it with one query, is checked again (a refusal rolls it back), and repeats the statements the condition held back. A delete of a row that is not stored reads the state the same way. On `postgres` and `pgvector` the condition reads the epoch row `FOR SHARE`, or plainly for a login that may not update the `value` column of `hb_gram_meta`. On the MySQL-protocol types, a write inside a transaction that was already open, while the index tables are absent, first reads the metadata table once to learn whether it was created after the transaction's snapshot. A write after the route's own registration retired an index of the entity, or created the index tables for another entity, reads it once. On those types, on an engine that may commit every statement, only the call's first row statement carries the condition, so a refusal still comes before any row is written; a call whose first `DELETE` removes no row sends one query at once. On `starrocks`, `mssql` and the generic `sql` type a write call sends one catalog or fingerprint query: the first after another workspace creates the tables sends two, and several calls in one transaction share what they read. A route without atomic upserts gives no all-or-nothing guarantee: the check runs before the later row statements, and where these commit on their own, a registration that commits after the check is not seen by them. The generic `sql` type has no portable form of the condition or the lock; name the server's own backend type to get both. 0.1.2.2 had neither the shared index nor this check. Use a transactional route that supports atomic upserts and rebuild locking, or pause writers while changing index options.

- **Transactions on dolt and OceanBase** (also in 0.1.2.2): an engine HeavenBase builds for a `dolt` or `oceanbase` server, a plain `hb.Database` included, runs transactions unless it is configured to commit every statement. Both servers report no autocommit flag when a connection opens, so PyMySQL never turned autocommit off: every statement committed on its own, a rollback undid nothing, and an `upsert` that failed part-way kept its earlier statements. Each new PyMySQL connection that did not ask for autocommit now turns it off.

- **seekdb routes with a `url`** (also in 0.1.2.2): a `seekdb` route configured with a `url` connects to the server the URL names. The local seekdb defaults (`localhost`, port 2881, user `root`) took the place of the URL's host, port and user.

- **Keyword index on seekdb and OceanBase** (also in 0.1.2.2): a registration of a `SparseGramIndex` field on a `seekdb` or `oceanbase` database that already holds the keyword tables, from another workspace or after a reopen, no longer fails with `Duplicate key name`: SQLAlchemy reads no index from those servers' `SHOW CREATE TABLE`, so each index was created again.

- **Keyword search on Oracle** (also in 0.1.2.2): `contained_in` through the SQL keyword index on an `oracle` route no longer fails with ORA-22849. The candidate lookup grouped by the keyword table's `CLOB` columns and counted distinct `CLOB` masks, which Oracle refuses; on Oracle the masks are now combined after reading the postings.



- **SQLAlchemy read classification**: `readonly=True` and `readonly=None` classify SELECT constructs by dialect-rendered SQL when structure alone cannot establish what they run, including ORM expressions and dialect-scoped prefixes, suffixes and hints. DDL through `text().columns()` invalidates the schema index.

- **Combined near filter metadata**: a non-exact near evaluated with its filter returns the filter’s metadata, such as `match`. Empty results declare the same metadata.

- **Json, Artifact and Array metadata on Chroma and Pinecone**: in 0.1.2.2 both backends silently left these values out of their metadata: every Json and Artifact value, and every Array of objects, mixed Array, empty Array or Array holding `None`. Pinecone also left out every Array that is not text. Placement accepts such fields on both backends, so those values were lost on write. Json values are now stored as their JSON text and Artifact values as base64 text, and both backends now claim `binary-storage: base64`. Pinecone documents a 40 KB metadata limit per record, so on Pinecone an Artifact larger than about 30 KB now fails the upsert with the provider's error instead of being dropped. Any other value the metadata cannot hold is stored as tagged JSON under the key `_hb_<field>` and decoded on read. When the metadata can hold a list's non-null items as a list (on Pinecone, only a text Array), it also keeps them there, so a native `array_contains` still matches them.

- **Large integers on Chroma and Pinecone**: some integers read back as floats in 0.1.2.2. On Chroma this was an integer outside the signed 64-bit range, in an Integer field or as an item of an Integer or untyped Array. On Pinecone, whose numbers are 64-bit floats, it was an integer beyond +/-2**53 in an Integer field (Pinecone dropped every non-text Array, as above). On Chroma every other item of such a list turned into a float too, so a native `array_contains` of an in-range item missed the row. Such a value is now also stored as tagged JSON and read back exactly. A scalar keeps its nearest supported float in the metadata. Chroma substitutes the largest finite float of the same sign when conversion overflows, and a list keeps only the items the metadata holds exactly. Native filters compared numbers near that float as rounded numbers. In 0.1.2.2, `n == 2**63 - 1` on Chroma matched a row holding 2**63, and `n == 2**53` on Pinecone matched a row holding 2**53 + 1. A filter whose operand is or holds a number of magnitude 2**63 - 2**10 or more on Chroma, or 2**53 or more on Pinecone, is compared using exact values on a portable route. A standalone Pinecone index has no unbounded row scan, so this needs a route that can supply the candidate rows. Smaller operands stay native.

- **No `_hb` column on Chroma and Pinecone**: a row with no field value was written with the placeholder metadata `{"_hb": true}`. Depending on which rows matched, reads returned it as an undeclared `_hb` column in backend rows and in query results, as in 0.1.2.2. Reads now leave it out, also on rows that 0.1.2.2 wrote. Chroma no longer writes the placeholder and removes it on the next upsert of such a row. Pinecone sends such a row without metadata.

- **LanceDB rows.** Arrow decoding keeps missing values as `None` and int64 fields as integers. Present vectors are writable NumPy arrays unless a present vector in that column holds a null element, in which case the column uses Python lists. `Array` fields are stored as JSON text and returned as lists. Added fields get nullable columns. Each upsert merge batch commits in its own transaction. A failed merge reports the provider error and stops later batches. Earlier batches and other clients' commits remain in effect. Unbounded native scalar queries return all matches with chunk-wise Arrow decoding. The `heavenbase.backend_defaults.lance.filter_limit` setting is retired. Use `.limit(n)` to bound a query. - **Invalid membership operands**: membership on numeric, Boolean, integer Categorical and Timestamp fields, and matching HyperG columns, raises `TypeError` for strings, bytes and non-iterable scalars.

- **Typed configuration snapshots**: overrides and stored layers with values that compare equal but differ in type use distinct snapshot identities. Mappings with mixed-type keys work in config reads.

- **Stored list and interpolation edits**: list writes edit the unresolved values seen by the written scope. A write through a list or a node interpolation preserves the other stored values and persists environment references instead of their resolved values. References that leave a copied node are adjusted to keep pointing to their original targets. A copied resolver other than `env` or `oc.env` refers back to its source expression. A resolver that yields a container, or a copy whose references cannot be preserved, raises `ValueError`. A list operation on a non-list value raises `TypeError`. Removing a missing key below a list or interpolated node saves nothing.

- **`heavenbase.modules.tags` export**: importing the submodule no longer shadows the public `tags()` function.

- **Collections reopen loaded on Milvus**: ensuring an existing collection loads it, so reads can reopen a Milvus Lite store after the process exits.

- **Entity-less id lookup**: an id outside one registered entity’s domain counts as absent there. If no present entity accepts the id, the error names the widest present domain. In a scoped MCP profile, inferring the entity from an object ID likewise skips visible entities whose `object_id` domain cannot hold that ID. In 0.1.2.2, `get`, `exists`, `set` and `delete` there of an ID longer than a narrower visible entity's `max_chars` failed with that entity's limit, even when a wider visible entity held the row. An ID that no visible entity accepts still raises, and the error now names the widest visible domain's limit. MetaSchema options and storage profiles can also be read through a route that uses a portable scan for row lookup.

- **Longer object ids**: SQL side tables and new Catalog tables accommodate longer ids. Milvus and StarRocks size new `object_id` columns for the entity’s id domain. Existing MySQL Catalog tables keep their 63-character `target_id` column and use portable filtering for equality, inequality and membership on that field. The shared SQL sparse-GRAM keyword table keeps a 191-character `object_id` column on engines that enforce the declared length.

- **Cheaper vector text, config reads and Registry refreshes**: a Vector stored as JSON text is encoded and decoded as plain JSON, without the walk over HeavenBase's tagged values; the stored text is byte-identical and text written by 0.1.2.2 still reads. Vector text holding a tagged object (`__obj_type__`), which no release writes for a vector, now raises `ValueError` or `TypeError` instead of being restored. `ConfigManager` reuses each scope generation and latest layer digest until the Registry publishes again or the config caches are cleared, instead of recomputing it on every generation refresh, and remembers at most `heavenbase.config.cache.max_generations` scopes (none when it is 0). `Registry.refresh()` that finds the stored snapshot at the published revision and digest verifies the digest against the payload and does not decode it again.

- **Database and SQL pools.** Explicit SQL read guards use the live dialect. Automatic transaction classification uses the executed SQL when text is needed. Ordered connection initialization statements distinguish SQL pools. Initialization commits before application use, so pooled reads preserve session settings and temporary data. PostgreSQL `SET LOCAL` setup is reapplied at each transaction start. Standalone DDL invalidates indexes for all setup variants after its transaction ends. DDL in `db.tx()` invalidates them when the statement runs and again when the transaction ends. Earlier reflections cannot refill the invalidated cache. SQLite recognizes DDL after leading empty statements and a UTF-8 BOM. The SQLite read guard accepts quoted names and schema qualifiers in inspection pragmas, including when a quote immediately follows `PRAGMA`. Within one Context authority, schema invalidation and drops cover every setup variant of one database (see **Database identity**). `SQLResponse` pickles from 0.1.2.2 with no query label restore and clone. `DatabaseDialectSpec` retains positional name-warning arguments. A synchronous nested read can use a connection reserved for a backend lock holder when its outer read holds a bounded-pool slot. Normal `pool_timeout` applies if the pool is exhausted. Equal or unhashable backend instances hold separate reservations.

- **Database identity.** Within one Context authority, schema invalidation and `drop_database()` group facades by the database they open, whatever their pool settings (including `pool.connect_args`), engine arguments, driver or `pragmas`, for every dialect, not only SQLite. Local files (SQLite, DuckDB) are grouped by resolved path, including symbolic links. Server databases are grouped by dialect, host, port, URL database, every URL query parameter, and the dropped namespace. User names and passwords do not separate groups, except on Oracle, where the namespace is the target user/schema. Facades that differ only in a URL query option such as `sslmode` stay in separate groups; pass such options through `pool.connect_args` to keep them in one group. A DuckDB drop no longer leaves another pool variant's connection open, which let a new facade read the dropped tables and lose writes it had acknowledged. DDL through one pool variant now invalidates the schema index of the others. This was already wrong in 0.1.2.2. A `drop_database()` that cannot remove anything (an in-memory database, a facade without a lifecycle namespace such as a server URL without a database or Trino, or a dialect without a registered database drop such as ClickHouse) does nothing to the database and disposes only the caller's engine, as in 0.1.2.2; other users' and pool variants' facades on that database stay usable. `heavenbase.database.drop_database()` does nothing for such a spec either, also as in 0.1.2.2. A drop of a file or namespace that is already missing still retires the group. A database drop (`Database.drop_database()`, every workspace, LLM cache or Capsule registry drop that removes a SQLite file or a server database, and the drops of the packaged LLM cache and Capsule registry files by `reset_default_local_state()`) also removes the engines and schema indexes that other Contexts cached on that database, including through a path alias of a local file, and closes their idle pooled connections, for server databases as well. Before, also in 0.1.2.2, another Context kept a pooled engine on a deleted SQLite file and handed it to its next opener, which served the deleted rows and wrote to the unlinked file. Only the dropping Context's facades are retired. Other Contexts' facades open a fresh engine at their next use, and their LLM cache and Capsule registry stores on the database reopen on fresh storage (see **Hidden storage after a drop**). A drop compares local files for path aliases before it takes the engine registry lock and visits each cached engine and schema index a fixed number of times, however many Contexts hold an engine on the database. Caching a new local-file engine also resolves the file's path before it takes that lock.

- **SQL batch and side-table fixes.** SQL deletes, ID lookups and sparse-GRAM statements bound each `IN` list by the dialect limit after accounting for other binds. Main row writes use one transaction on transactional engines. SQL preserves the input insert order across optional column sets. Upserts through the `mysql` (including MariaDB), `dolt`, `seekdb` and `oceanbase` backend types preserve case-distinct row IDs and sparse-GRAM postings, and their new tables use case-sensitive collations chosen from the server version, no-pad where supported. StarRocks, `mssql` and `trino` compare IDs as their server does, as in 0.1.2.2. The generic `sql` type does too, but on a dialect not known to compare exactly each write call first reads the stored IDs the server matches: an upsert whose ID matches a different stored spelling raises `ValueError` and that backend call writes nothing (before, and in 0.1.2.2, it replaced the other spelling's row), and a delete of an ID not stored exactly removes nothing.' A collision with an existing primary key reports a duplicate-key error and preserves the stored row. StarRocks upsert and delete predicates use StarRocks-compatible SQL. If a SQLite trigger rolls back a top-level upsert or standalone statement, the original write error is reported. SQL write batches and sparse-GRAM maintenance cap their bind budget at the active SQLite connection’s limit when the driver exposes it. A SQL side-table field added to an existing entity reads as `None` for rows that predate it, including on DuckDB. Existing side-table items remain readable. The SQLite batch regression enforces a statement bind limit before exercising large writes and deletes. On the MySQL-family backends, side-table reads (`get`, `get_many`, `scan`, `iter_scan`, `scan_page`) and Array and HyperG filters find side rows through the side table's `object_id` index, and still match only the exact ID when the main table was created with a different collation. SideTable Array and HyperG items read back in the order they were written on the `mysql`, `dolt`, `seekdb` and `oceanbase` backend types. `JSON_ARRAYAGG` takes no `ORDER BY`, so items came back in the order the server read them, often sorted by value. This was also present in 0.1.2.2. SQLite and DuckDB no longer rely on the query plan for this order. For the `json_arrayagg` and `json_group_array` styles, `SQLDialectSpec.side_table_json_agg_expression` now aggregates `[position, payload]` pairs, and the new `SQLDialectSpec.side_table_json_agg_items` returns the payloads in order.

- **SQL routes that share a database.** SQL routes that store fields of one entity in the same database write each row once, with every route's fields, through the first route by name, and share one sparse-GRAM publication transaction. Each field is written as its own route stores it, in that route's column or side table (a `pgvector` route keeps `SideTable` fields in its main table). HeavenBase decides which routes share a database while it registers the entity, after every route has created its tables and before anything is published, so the routes agree even when the registration itself creates the database file or tables, and the check needs no extra connection while a publication transaction is open: routes that share an engine, open the same SQLite or DuckDB file, reach the same PostgreSQL database with matching roles and search path or resolve the entity's table name to the same PostgreSQL table, or reach the same current database of one server through the `mysql`, `dolt`, `seekdb` or `oceanbase` backend types (by a named lock). Routes of the generic `sql` type, and MySQL-family routes of a server without the named-lock functions, are recognized by a table made for the check: when one route's table holds another route's columns, it creates a table `hb_probe_...`, the other route looks it up in its own default schema, and the table is dropped. Where the server refuses to create it the routes are not recognized, as in 0.1.2.2; where it refuses to drop it a `RuntimeWarning` names it. PostgreSQL routes that write one table but resolve different keyword index tables raise `ValueError` when either binds a `SparseGramIndex` field. PostgreSQL routes are recognized by the database they reach and their roles and search path, whether or not the database holds a sparse-GRAM index. If a server cannot be asked, the registration fails with a `RuntimeError` whose `__cause__` is the original error; register the entity again once the server answers. This also holds for the sparse-GRAM publication check of such routes, which before raised the server or driver error itself (for example a psycopg2 `OperationalError` on PostgreSQL). Before, on SQLite, DuckDB, PostgreSQL and MySQL, each route that split an entity on one database replaced the row with only its own fields, whether or not the routes shared an engine and whether or not the database held sparse-GRAM tables, so the other route's fields were lost or a required field failed the write with a NOT NULL error; MySQL routes that split sparse-GRAM fields failed the first write with a lock wait timeout; and on PostgreSQL a `SideTable` field of a `pgvector` route was not written. This was also present in 0.1.2.2. When the first route by name binds no `SparseGramIndex` field of its own, it ensures the keyword index tables while the entity is registered. Before, its first write ran that DDL inside its row-write transaction, so with a one-connection pool (`pool_class` queue with `pool_size` 1 and `max_overflow` 0, static, or assertion) every write and delete of the entity failed with a pool timeout, "connection is already checked out", or on PostgreSQL "set_session cannot be used inside a transaction". If ensuring those tables fails once during registration, the routes still write each row together, and the next write ensures the tables before it opens its write transaction, so a one-connection pool keeps working (a write made inside an already open transaction still ensures them inside it). On other SQL backend types (`oracle`, `mssql`, `starrocks`, `trino`, `clickhouse`), give such routes separate databases.

- **pgvector storage.** A `pgvector` route ensures its table the way the other SQL backends do, keeping `SideTable` fields in its main table as before. It keeps no sparse-GRAM keyword index (see the read-first list).

- **In-memory and file reads and writes.** In-memory membership finds rows containing an Array item. Equality and membership find rows indexed by a single-field unique constraint. File backends enforce unique constraints before any record changes and persist `compare_upsert` under a folder lock shared within the process. No lock coordinates several processes, as in 0.1.2.2: use one writer process per folder where `compare_upsert` has to hold, and stop the writers of other processes before dropping a folder. A record file that is a symbolic link to itself reads as missing instead of raising `RuntimeError`; a write to it still raises. Reloads parse only files whose inode, size or modification time changed. Each record change reaches memory after it succeeds on disk. Counts omit the superseded file if a move to a hashed name was interrupted. A JSON `upsert` costs about 5 to 9 percent more than in 0.1.2.2, mainly because the backend reads a record's stored ID before overwriting it. JSON and pickle reads return detached values. Pickle point lookups deserialize each returned row once. Pickle records retain their stored object behavior and cyclic references. Backend-ready `RowOp` copies preserve cycles and shared references, and `copy_data` reuses immutable leaves. The Windows file regression checks the temporary path actually created.

- **Chroma filters.** Same-operator clauses are flattened and regrouped in lists of at most 32 operands to stay within SQLite expression-depth limits. On every backend, very long chained Python expressions can exceed Python's recursion limit. Use `Or(clauses=[...])` or `And(clauses=[...])` for long lists.

- **Pinecone and Milvus records.** Pinecone keeps its client after a failed metric lookup so later queries can retry. Patches and GraphEdge rewrites fail before writing when a required Pinecone source misses. In 0.1.2.2 and 0.1.2.3, a successful Pinecone fetch can return an older version of a row. Pinecone's eventual consistency gives a patch no proof that the fetched values include another client's latest write. A `set` or `set_many` that merges those values can overwrite a recent update. When this matters, coordinate writers and build a full upsert from authoritative row data, or keep the row on a store with the read consistency the application requires. A Pinecone fetch can miss a recent write. It has no documented visibility bound or conditional create, so a negative fetch cannot establish that an ID is absent. When no route can establish absence, `upsert` and `upsert_many` with `overwrite=False`, mutating entity inference, `set` or `set_many` on a new ID, and confirmed GraphEdge repair of a missing target raise `ValueError`. The visibility limit also affected 0.1.2.2. The explicit refusal replaces cases that could overwrite an existing record or behave as if the ID were absent. Pass `entity=` to bypass inference. Use a full upsert with `overwrite=True` if replacement is safe, or retry a patch of an existing row once the record is visible. Use a route with complete and authoritative row coverage when the operation needs to prove absence. GraphEdge deletion of such a target checks its incoming references as for a present target: a restriction blocks it, detach rewrites the references, and the record and its Catalog row are deleted; the call returns `False` for that target. When one of the target's oldest routes can show its absence, deleting an absent target returns `False` and confirmed repair removes edges to targets absent from every route, as in 0.1.2.2. After a Pinecone fetch miss, `upsert` and `upsert_many` with `overwrite=False` no longer silently replace the stored record, as 0.1.2.2 did (see the behaviour changes). Deleting a row of an entity stored only on Pinecone after a fetch miss, with that entity given, also deletes its Catalog row, which 0.1.2.2 left behind; the call still returns `False`, because no route returned the row. As in 0.1.2.2, deleting an explicit Pinecone-only target can return `False` even when the delete removes the record. The return value comes from the preceding fetch, which may miss because of eventual consistency. Treat `False` as a fetch miss and verify deletion through an authoritative source if confirmation is required. With an entity stored only on Pinecone, an inconclusive Pinecone fetch miss now aborts `delete`, `delete_many`, `set` and `set_many` without `entity` even when no other entity holds the ID. On the workspace they raise `ValueError` asking to specify the target entity explicitly. Before, the workspace `delete`/`delete_many` reported `False` and kept the record, and the workspace `set`/`set_many` raised `TypeError` ('set with a plain dict for a new object_id needs entity=...'). Before, in a scoped MCP profile, `delete`/`delete_many` reported `deleted: False`, and `set`/`set_many` raised the 'could not resolve object_id ... inside MCP profile ... entity scope; pass entity=...' error. MCP tools report both the old and the new error as a tool error (`RuntimeError`). 0.1.2.2 behaved like the old workspace and MCP behaviour above. Behaviour with an explicit entity is unchanged. Chroma and Pinecone preserve explicit nulls in nullable metadata fields with defaults when they store a record. Re-upsert older rows whose cleared metadata key was omitted. Built-in Milvus `Json` fields store scalar JSON text in marked wrappers. Objects and arrays retain their 0.1.2.2 layout, including objects with only the former wrapper key. Reads preserve mappings stored by custom logical types. HeavenBase 0.1.2.2 exposes the new scalar wrappers as objects. Milvus Lite integration tests require both optional packages. Tagged Json values returned as parsed data restore their original HeavenBase types.

- **Configuration caches and edits.** Cacheable configuration reads use one capture of each referenced environment value for interpolation and cache identity. Native `oc.env` and expressions with unresolved dependencies are evaluated live. Positive and negative zero have distinct identities, including in nested values and mapping keys. Nested list insertions populate the inserted item, and edits preserve literal dots in escaped keys. Composed strings with literal environment references, including hyphenated names, reuse snapshots until a referenced value changes.

- **Default Context and serialization.** Omitted configuration uses the installed Context across predicate compilation, handler construction, toolkit config and serializers, profiles, and the aggregate code-reduce guard. A supplied bound resolver selects its own Context's profile config. Global log configuration resolves relative paths, home and environment variables at the call, preserving symlinks and HeavenBase path aliases. If the current directory has vanished, the relative path is saved as given. `json.dump(..., cls=HbJsonEncoder)` tags HeavenBase values as `json.dumps` does. Global log paths preserve literal variable markers and trailing filename whitespace introduced by expansion, and Windows extended-drive prefixes survive the round trip. Restoring a temporary default to the unselected state or creating a Context that owns `CM_HVNB` discards temporary process-only scopes. Later writes use the owning Context's Registry. Context reset invalidates config generations and snapshots. A snapshot can retry if reset retires its Registry during refresh. Backend lookup captures a stable reference during close and completes composition on the current backend when reset overlaps initialization.

- **Hidden store reset.** `reset_capsule_registry(drop=True)` drops and retires the Capsule registry stores of every selected Context even when a drop raises, then raises that error (several failures are combined into one `RuntimeError` chained from the first); later stores and later Contexts are no longer left undropped and still in use. It drops only the Capsule registry's hidden storage. Other hidden stores of the Context, such as the LLM cache's persisted responses, are kept unless they share the dropped storage (a backend, an engine or a dropped local database file). Previously every hidden store was dropped, in 0.1.2.2 as well. A hidden store of any Context that shares it, an LLM cache's or another Context's Capsule registry's, is detached as **Hidden storage after a drop** describes: it reopens on fresh storage at its next use, and a later drop of the store still drops every route it opened. A cached call that starts during the drop, in any Context, waits for the drop and then works on fresh storage. A thread of the dropping Context that has a connection in use on the dropped database raises `RuntimeError` instead of waiting for the Context lock, which `LLMCache.reset(drop=True)` and `reset_capsule_registry(drop=True)` hold while they drop, and instead of waiting for the drop; 0.1.2.2 dropped these stores after releasing the Context lock. A process-wide `reset_capsule_registry(drop=True)` reaches every open root Context of the process, including the default Context once it exists, even one that never used a Capsule registry, wherever its configured registry storage may exist. Each such open Context's configured registry storage is dropped even when its facade never read it. A closed Context is skipped. A Context that a `Context.close()` or `reset_default_local_state()` has marked counts as closed for the process-wide form: configured storage that nothing has opened yet is skipped and the reset returns, and a drop of open storage raises `RuntimeError`. If that close or reset gives up, the Context is open again and still serves the rows. This includes a Context whose registry facade was already garbage-collected. Previously, also in 0.1.2.2, such a Context kept its Capsule rows and the reset returned normally.

- **Dropping resets of storage nothing opened yet.** `LLMCache.reset(drop=True)` and `reset_capsule_registry(drop=True)` now drop the storage that the `heavenbase.llm.cache` or `heavenbase.capsule.registry` configuration names in each selected open Context, even when no store on it is open yet, for example in a new process or a new Context over the same root as an earlier one. Before, also in 0.1.2.2, they dropped only the stores this process had already opened, and returned normally; the next call then served the old cache rows (plaintext prompts under the default configuration) or the old Capsules. The dropping process-wide forms reach every open root Context of the process, including the default Context once it exists, whether or not that Context used the LLM cache or the Capsule registry. No default Context is built for a reset. A drop opens the configured storage only when it may exist. Storage whose routes are all local files that do not exist is skipped, so a Context that never created it is not initialized; storage on a server database is opened. A non-dropping process-wide `LLMCache.reset()` touches only the Contexts that hold a cache store. A Context discarded without `close()` stays open until it is garbage-collected, so a drop still reaches it; close Contexts you no longer use. An unowned `CM_HVNB` passed as `config_manager=` selects the default Context, as `LLMCache.current()` does; in explicit Context mode it selects none, and the reset returns as before. A closed Context, the closed default included, is skipped: it owns no storage, so its rows stay on disk and the reset returns. A Context that a `Context.close()` or `reset_default_local_state()` has marked counts as closed for `LLMCache.reset(drop=True)`, named or process-wide, and for the process-wide `reset_capsule_registry(drop=True)`: configured storage that nothing has opened yet is skipped and the reset returns, and a drop of open storage raises `RuntimeError`. If that close or reset gives up, the Context is open again and still serves the rows. If the configured store of an open selected Context cannot be opened, the reset raises that failure unchanged, as for a failed drop, but only after every other selected store has been opened, dropped and retired. Several failures are combined into one `RuntimeError` chained from the first.

- **Process-wide dropping resets reach every open Context.** A process-wide `LLMCache.reset(drop=True)` or `reset_capsule_registry(drop=True)` now drops the configured storage of every open root Context. This includes a Context that never used the LLM cache or the Capsule registry, so it no longer keeps serving its old cache rows or Capsules. Before, also in 0.1.2.2, such a Context kept its rows and the reset returned normally.

- **Serializer whose Capsule was dropped.** One registered MCP serializer whose Capsule was removed by `reset_capsule_registry(drop=True)` no longer makes profile resolution, workspace Toolkit builds and assistant calls that do not use it fail with `SourceUnavailable` (also in 0.1.2.2 after a drop scoped to one Context). - **Hidden storage after a drop.** A drop of a SQL database removes it for the whole process: every LLM cache and Capsule registry store of any Context whose workspace has a SQL backend on the database, also through another path to a local file, is detached and opens the database again, recreating its tables, at its next use. Its routes on other storage keep their rows, and a later drop of the store (`LLMCache.reset(drop=True)` for a cache service's store, a Capsule registry drop, or a `reset_default_local_state()` of its Context) still drops every route it opened. This holds for every `Database.drop_database()` that removes a database and every `Database.drop()`, so for workspace, LLM cache and Capsule registry drops, Context resets and direct calls alike, and also for a store that is opening its workspace while the drop runs: it waits for the drop to end and builds its workspace again instead of attaching one whose tables the drop removed, and a build that fails while the drop runs is tried again once it ends. The next drop of a database that a discarded build used first waits until the stores it made build again have built, for at most ten seconds in all. Stores with one storage configuration build one at a time, across Contexts, so a store whose rebuild has not ended within that time can be postponed again. Drops of one database through `Database.drop_database()` and `Database.drop()` run one after another when they overlap: from any Context, also from two threads of one Context, and through any name of a local file that the process opened or dropped while the file existed (a hard link, or another letter case on a case-insensitive file system), also after that name is gone. So a table drop no longer connects to a file that another drop is removing. A table drop of a facade that a running `drop_database()` of its Context retires then fails with "Engine has been disposed", as the same calls in sequence do. The module-level `heavenbase.database.drop_database(spec)` deletes the database without the drop locks and detaches no store, as in 0.1.2.2. It now refuses a thread with a connection to the database in use, and it closes HeavenBase's connections to a DuckDB file first. The drop waits for the LLM cache hit bookkeeping already started on such a store, so a hit never counts on an entry written after the drop; any other call already running on it when the drop starts can fail once. LLM cache drops, Capsule registry drops and Context resets also detach, before dropping anything, the stores that share a database or a Backend object with the stores they drop, and keep every store with the storage configuration of a dropped or detached store from opening until they end: a call that starts on one meanwhile, in any Context, waits for the drop and then opens fresh storage. Hidden stores with the same storage configuration open one at a time, across Contexts. A store builds its workspace and registers its entities under its Context lock, which workspace construction also held in 0.1.2.2. So the stores of one Context open one at a time, and an LLM cache or Capsule registry open, which builds a workspace, holds up that Context's other writes until it ends, as every workspace construction did in 0.1.2.2. On Python 3.12 the build takes one to two seconds in a Context that already built a workspace, about three seconds as a fresh Context's first workspace, and about four and a half as the first in the process. Stores of other Contexts with other storage configurations open independently, as in 0.1.2.2. A store that must wait for a drop that ran while it opened waits outside the Context lock, unless its caller already holds it. `reset_default_local_state()` drops the local database files of the packaged LLM cache and Capsule registry configuration like any database, so another Context over the same root no longer serves their deleted rows. It still deletes the Context's own SQLite system database file directly, without the engine registry, so another Context's engine on that file stays on the unlinked file, as in 0.1.2.2. In 0.1.2.2 no drop reached another Context's LLM cache or Capsule registry on the same database: after a drop that removed a SQLite file it served the deleted rows from the unlinked file and lost its writes until it was reset, and after a table drop (`Database.drop()`) every call failed with "no such table".

- **SQLite journal files after a workspace drop.** A SQLite workspace drop (`SQLBackend.drop()`, which LLM cache and Capsule registry drops and Context resets also use) deleted the database's `-wal` and `-shm` files a second time, after `Database.drop_database()` had returned and outside the drop. The files are now deleted only inside `Database.drop_database()`, together with the database file, and nothing is deleted after it returns. This was already wrong in 0.1.2.2.

- **SQLite files reached through a symbolic link.** Each SQLite connection opens the file by the path its symbolic links resolve to when the connection opens, so every symbolic-link name of one file reaches one database and shares its `-wal` and `-shm` files. This was already wrong in 0.1.2.2. An open SQLite facade can retain the original target's database key when its symbolic link is retargeted, as in 0.1.2.2. - **File records and store folders past `MAX_PATH` on Windows.** Without long-path support (`LongPathsEnabled` 0, the Windows default), the JSON and pickle File Backends create, read, write, list, delete and drop store folders and record files whose path is too long for Windows through the extended-length `\\?\` form; `FileBackend.path` keeps its ordinary form. - **Local model servers and the system proxy.** On the `openai`, `anthropic`, `portkey` and `bifrost` gateways, a `base_url` on this machine (`localhost`, a `*.localhost` name, or a loopback address such as `127.0.0.1` or `::1`) is reached directly. The environment's proxy variables and the system proxy (the Windows registry, macOS System Configuration) do not apply to it, unless `http_proxy` or `https_proxy` is set on the LLM, passed to the call, or set by a `NetworkProxy` block open on the calling thread or task (a block does not reach the worker threads on which `embed` sends its requests). A client built for such a proxy is kept for requests that name the same proxy settings. Calls or blocks with different proxies that overlap can build a client with another one's proxy, as in 0.1.2.2, where such a client also served requests that name no proxy. The SDK clients read the system proxy but not its bypass list, so before, also in 0.1.2.2, a local model server was sent through the system proxy and failed when that proxy could not reach it. Remote endpoints keep their proxies: as in 0.1.2.2 their SDK client is shared whatever the proxy settings, so it keeps the proxy of the call that built it, and later calls that name another proxy, also one after another, are sent through the first. With `gateway="litellm"`, loopback model URLs may still use the system proxy, as in 0.1.2.2: LiteLLM constructs its own HTTP clients, outside this bypass. Configure a loopback bypass for the LiteLLM client or select a HeavenBase SDK gateway that supports the endpoint.

- **DuckDB drops of a file in use.** On DuckDB, `Database.drop_database()`, and so every workspace, LLM cache or Capsule registry drop of a stored DuckDB file, removes the database for the process also while another call of any Context is using the file. DuckDB keeps a database open in the process while any connection to its file is open. So the drop first closes every connection of HeavenBase's engines to the file, or to another name of it: idle ones in whichever pool they sit (also a pool that a dispose replaced), and each one returned meanwhile. It waits for connections in use. Opening a connection to the file waits for the drop before DuckDB opens the file, and then reaches the file as the drop left it. A thread that holds a Context or workspace lock (such as a workspace write) or another connection to the file fails at once with `RuntimeError` instead, because the drop may be waiting for that thread. When connections stay in use for 30 seconds, such as one in another thread's long transaction, the drop raises `DropRefusedError` (a `RuntimeError`) and removes nothing. Before a workspace drop drops any route, it checks every route for a connection of the dropping thread. It then waits up to 30 seconds per DuckDB file, one file after the other, without holding a lock and without closing a file, until every connection that was in use when the wait for that file began has been returned; steady short reads do not prolong it, and a connection through a hard link of the file is waited for only by the drop itself. Either refusal raises `DropRefusedError` with no route dropped and the workspace usable. It then drops its routes in order under the workspace and Context locks. A connection lent after that wait began can still make a DuckDB file's drop wait there and refuse after 30 seconds. The routes after it are then kept, the drops of earlier routes that succeeded stay in effect, the error says which routes were dropped and which routes' drops failed with another error before the refusal, or that no route was dropped when neither happened, and another `drop()` drops the routes that were kept. These checks cover stored databases (an in-memory one belongs to one facade, so nothing else can hold it); a failure of a route's own removal, such as Windows refusing to delete a SQLite file that a connection still holds open, can still come after earlier routes were dropped: `Database.drop_database()` then raises `PermissionError`, and a SQL workspace drop falls back to dropping that database's tables, as in 0.1.2.2. Opens and closes of connections to one DuckDB file now run one at a time, because DuckDB can fail an open with "Unique file handle conflict" while another thread closes the last connection to the file. A close that a garbage collection starts inside an open runs right after that open. If such a close fails, the failure is logged and changes nothing else. A forked child does not wait for an open that was running in its parent. DuckDB's `<file>.wal` file is removed with the file. Before, also in 0.1.2.2, a drop that overlapped a call on the file unlinked it while the database stayed open. Its rows stayed readable, also through facades created after the drop, writes made after the drop were lost once the process closed the database, and the `.wal` file stayed behind. These refusals are new in 0.1.2.3. A connection whose close has begun but not finished no longer counts as open, so a call that opens the file in that moment can still reach the removed database, as in 0.1.2.2. Retry the write after the drop finishes. Drain responses and end transactions on the file before retrying a refused drop.

- **Interrupted database calls.** A call that a signal handler interrupts (Ctrl-C, an alarm) leaves the lock of the engine registry, of the DuckDB keyword-index write gate and of a SQL backend's reads free. An interrupt can still leave SQLAlchemy's connection pool, DuckDB's own connect or a DuckDB file's open-and-close gate in a state where later DuckDB calls wait; 0.1.2.2 has the first two. When beginning a transaction is interrupted or fails, its connection is closed and the thread's later writes run in transactions of their own and commit. A SQL backend's drop that is interrupted while it waits for running reads admits reads again. These locks are new in 0.1.2.3. An interrupt that arrives while SQLAlchemy returns a connection to its pool can still lose that connection to the pool, as in 0.1.2.2. After an interrupt cut off the return of a connection that a DuckDB queue pool keeps, a drop of the file waits 5 seconds for that connection while its connection object is still referenced, and then closes it, and so does the module-level `drop_database()`; drops on static, singleton and assertion pools do not wait for it. On a `StaticPool`, when a thread has checked out the stored database's one connection twice and returned the inner checkout, its own drop of that database is not refused while the outer use is open. The drop succeeds and closes the connection under the outer use, whose next statement fails. In 0.1.2.2 that happened only to a drop made through the facade that owns the static pool; after a drop made through another facade the outer use went on.

- **Drops from a transaction.** A thread that has a connection of HeavenBase's engines in use on a database can no longer start `Database.drop_database()`, `Database.drop()` or `heavenbase.database.drop_database()` of it, and so no workspace, LLM cache or Capsule registry drop either. In use means an open transaction, or a streamed response it has neither consumed nor closed. This applies to a stored database; an in-memory database is not checked. The call raises `DropRefusedError` (a `RuntimeError`) at once. Before, also in 0.1.2.2, on MySQL the drop's statement waited for that thread's own transaction until `lock_wait_timeout` (one year by default), also while another drop of the database was running. On SQLite and DuckDB the drop removed the file under the open transaction.

- **Dropped responses release their connection.** A streamed read's `SQLResponse` that is dropped before its rows were drained or it was closed now rolls its statement back and returns its connection at once, where its last reference goes. Before, also in 0.1.2.2, the connection stayed checked out until a garbage collection freed it, because SQLAlchemy's Connection and its transaction refer to each other. `Database.available(check=True)` closes the response of its probe. A response that a garbage collection frees together with an iterator over it keeps its connection until the `heavenbase-sqlresponse-settler` thread has read its remaining rows and ended its transaction. That connection does not count as in use by the thread that executed the response: that thread's calls may wait for a drop, and its own drop first settles such responses itself.

- **Abandoned iterators of streamed reads.** An unfinished `SQLResponse` iterator freed by the same garbage collection as its response commits the read's writes. Before, the collection reset the statement's connection first and rolled them back (also in 0.1.2.2). A call on another thread that finds a lazy `SQLResponse` cursor already finished waits for the statement's transaction to end. Before, it could return before a commit was visible (also in 0.1.2.2).

- **Drop file removal.** A drop of a stored SQLite or DuckDB file no longer fails when the close of the database's last connection removes a `-wal`, `-shm` or `.wal` file between the drop's check and its removal (also in 0.1.2.2).

- **Assistant session log retries.** Within one Context tree and log workspace, only one turn runs per conversation at a time. Completed retries replay the stored answer, and provider attempts have distinct trace event IDs. A disconnected stream stops waiting before starting a retry. Admission retries authoritative reads once and stops before provider I/O if the retry fails. Sealing uses a durable per-conversation counter and avoids fetching previous answers after the counter is initialized from retained summaries. Transcript repair uses seal order and preserves the recorded relative order of older turns. Full questions and answers are retained in transcript payloads, and searchable text is bounded. A new turn, a completed replay, or an explicit rebuild can restore a missing session from retained turns without evicting another conversation. A blank replay can restore the session and stays out of the transcript. Append and replay repair failures report `capture_warning`. A retained turn can be replayed by `turn_id` alone. A retry that changes the recorded question or workspace is rejected. Retention eviction, retry-attempt detection and trace existence checks read only row ids and coordinates on backends that group natively (SQLite), not every stored provider request and message. Turns of conversations already in the log do not wait for an eviction's reads and planning, but they wait for its single bulk delete like any concurrent write to the log workspace; new conversations are admitted one retention pass at a time, and a turn on a conversation being evicted waits for the eviction. `rebuild_session`, replay repair and session restore re-aggregate usage with the same merge as live appends (numbers add up, and a number replaces a stored value that is not a number, such as null; any other value keeps the first non-empty one), so a rebuild leaves `session.usage` as the appends left it.

- **Assistant session log ids.** With the session log enabled, a dashboard assistant request that gives neither `conversation_id` nor `turn_id` opens its own conversation, and a turn without `turn_id` is its own turn, even when two requests start in the same clock tick. (A request that gives a `turn_id` but no `conversation_id` keeps its stable derived conversation, so a retry still reuses it.) Missing ids were derived from the wall clock, so on a coarse clock (Windows CPython before 3.13 advances `time.time()` about every 15.6 ms) the second request could replay the first request's answer without calling the provider, or fail as 'already recorded for a different question or workspace'. Missing ids now come from a random token. New in 0.1.2.3 (the session log is new); no 0.1.2.2 behaviour changes.

- **Agent session ids.** A `Session` created without an `object_id` gets its default id from a random token instead of the clock, in the same id format. Before, also in 0.1.2.2, two sessions with the same title and `agent_ref` created in one clock tick got the same id, and the second overwrote the first. This affected CLI chat logging, `log_chat_session`, MCP call-log sessions and `Agent` sessions. An `object_id` the caller passes is kept.

- **Usage totals.** Usage is the same whether a call's rounds were streamed or not. A response that reports prompt and completion counts but no total gets `total_tokens` as their sum on non-streamed calls too (`stream_chat=False`), and a tool loop sums every round's total. Before, also in 0.1.2.2, one round's reported total stopped the derivation for the others, so a two-round call reporting 15 and then only 30/4 gave `total_tokens` 15 instead of 49 when not streamed. A streamed response whose counts arrive in several usage chunks gets the total of their sum (a stream reporting prompt 10 / completion 0 and then completion 5 gives 15, as unstreamed); each stream chunk keeps the counts it reports, as in 0.1.2.2, and the response derives its total once. A merged total is the sum of the totals the parts report plus prompt plus completion over the parts that report none. The CLI usage line follows the same rule. A streamed assistant turn (`assist_stream`) records the same usage as a blocking `assist` turn: both merge the usage of every provider response of the attempt (each round's usage as `LLM.chat` reports it, a streamed round deriving its `total_tokens` from the prompt and completion counts when it reports none, plus the turn's compaction summaries; see **Assistant turn usage**), and the turn row keeps the first reported value of a non-numeric key such as `prompt_tokens_details`.

- **Assistant turn usage.** A successful session-logged assistant turn records the usage of every provider call of its attempt: each tool-loop round plus the turn's own compaction summaries (`replay_compaction` for the replayed history, `turn_compaction` inside the tool loop). The session usage merged from it follows. A successful turn with a blank answer adds its usage to the session exactly once without adding transcript messages, also when the session is rebuilt or repaired on replay. Before, those compaction calls were logged as response rows but left out of the turn's and the session's usage. A response counts when it arrives, so under degraded capture the usage can include a response whose row failed to write. An errored turn records no usage, and a successful retry records only its own attempt. An injected `llm` runtime is not traced and records the usage it returns.

- **Request trace fingerprints.** Tracing records normalized messages, tool schemas, options and routes before gateway conversion. Response and tool-choice schemas and the prompt cache key are retained. The fingerprint sorts JSON keys after encoding, takes the last value for duplicate encoded keys, and escapes lone surrogates. Read-only mappings serialize as JSON objects, including when nested, and fingerprint identically to equivalent dictionaries.

- **Portable text predicates.** LIKE and ILIKE match wildcard segments in time linear in input length for a fixed pattern. The regex scanner routes costly supported patterns through a bounded-state matcher. Patterns that exceed its state cache can still be expensive.

- **Workspace and replica reads.** Registry retries retain iterator-supplied extension roots. A tracked workspace can enable an explicit `SparseGramIndex` and reopen by ID. Replicated Json values compare large integers without rounding through float64. Dependency metadata refreshes when a requirements file or the package version changes. Strict replica reads also distinguish JSON Booleans from numbers inside objects and arrays. An unchanged `WorkspaceSpec.register` call refreshes the durable registry before returning. `WorkspaceSpec.unregister` sees workspaces registered by another Context. Registration reads current MetaSchema options and uses native key filters where available. Schema publications record their projection IDs for direct lookup on reopen and remove obsolete rows. Replicated Float values holding equal infinities, or NaN on every route, no longer read back as a cross-route conflict; 0.1.2.2 raised the same false conflict. Strict reads (`unique=True`) compare byte values (`Artifact` fields) of routed replicas exactly. Different replicas that look like numbers, such as `b"42\n"` and `b"42"`, now raise 'not unique across routed backends' instead of returning the first route's value. 0.1.2.2 compared them as numbers.
- **Query rows deleted before hydration.** A query (`filter`, `near`, or both, and near aggregates) no longer returns a matched row that was deleted between the backend query and hydration when one of the entity's oldest routes shows the row is absent, as such a route on any backend other than Pinecone does; 0.1.2.2 returned it as a row holding only its id and the values the backend query supplied. An entity whose oldest routes are all on Pinecone keeps the 0.1.2.2 result for a match that no fetch returns: a Pinecone fetch miss does not show the row is absent, so the match is kept with the query's values, also when it was deleted after the query. Before keeping it, the backend fetches the match again with a short backoff, bounded by `PineconeBackend.miss_settle_seconds` (5 seconds by default) plus the fetch in progress, and hydrates it from a later fetch that returns it. The wait runs inside the query, which holds the workspace read lock, so writers of the workspace wait for it. An index-view LSN on a fetch response only ends the wait early; Pinecone documents that LSN for queries, not for fetches, so a fetch may report none, and then the backend fetches only once more. An error on one of these retries, such as a timeout, ends them and keeps the query's values; it neither fails the query nor drops the Pinecone client. As in 0.1.2.2, a near match on an entity whose oldest routes are all on Pinecone can survive deletion between search and hydration. A fetch miss can reflect index lag. HeavenBase retries the fetch, uses a later result if one is returned, and keeps the match with the query's values if the fetch continues to miss. Use an authoritative route to verify current presence when acting on the match.

- **Lagging Pinecone hydration fetches.** A near match on an entity stored only on Pinecone that a lagging hydration fetch missed is hydrated from a later fetch, so it carries the fields the query does not return, such as its vector, instead of only the query's values. This was also present in 0.1.2.2.

- **A route added by a replacement no longer settles absence**: after `register(..., allow_replace=True)` added an InMem or SQL route to an entity stored on Pinecone, a Pinecone fetch miss let the new route, which holds none of the rows stored before, show a stored row absent: a create-only upsert replaced the record and entity inference patched another entity's row. For routes added by this release, only an entity's oldest routes now settle absence. Also in 0.1.2.2, which treated every miss as absent.

- **LLM cache maintenance.** The storage of an authority's cache service (the caches `LLMCache.current()` returns) belongs to its Context, which keeps one store per storage configuration for every such cache, garbage-collected cache objects included, so a collected cache no longer leaves an open store behind. `LLMCache.reset(config_manager=...)` retires the Context's stores and `drop=True` drops their storage on every route first; the process-wide `LLMCache.reset()` does this for every Context. Before, also in 0.1.2.2, each cache object opened its own store, the Context kept every one of them open, and a reset reached only the live registered cache, so after a short-lived `LLM(context=...)` was collected, `reset(drop=True)` dropped nothing and the rows were served again. A cache built from a configuration (`LLMCache(...)`, `LLMCache.from_dict`, `cache_config=`, a `cache=` mapping) owns its store, which is released with it; a reset does not reach it, and a `reset_default_local_state()` drops it while the cache object is alive (0.1.2.2 kept such a store open after its cache was collected, so a reset dropped it then too). Caches on dropped storage reopen as **Hidden storage after a drop** describes. Non-dropping resets release idle local-file connections. After `reset_default_local_state()`, `LLMCache.reset(drop=True)` drops the cache's configured storage again, which holds only rows written since the reset. After `Context.close()` it returns without dropping anything: a closed Context owns no storage, and its rows stay on disk, as in 0.1.2.2. A dropping reset also drops configured storage that nothing opened yet (see **Dropping resets of storage nothing opened yet**). The cache opens new storage at its next call. SQLite and PostgreSQL cache hits update access metadata in place when the entry's identity and creation timestamp match, preserving later replacements and evictions. A drop waits for the hit bookkeeping that another cache already started on the dropped storage, so a hit never counts on an entry written after the drop, also where two entries share a creation timestamp (a coarse clock, or MySQL's single-precision `FLOAT`). Warm caches in separate Contexts on independent storage can record hits concurrently. Hits within one Context share its workspace write lock. Forked workers receive fresh cache and hidden-storage coordination locks.

A server that stops before serving for another reason, such as a failed application startup, exits with Uvicorn's startup-failure status (3). `serve()` and `run_server()` raise `SystemExit` with the same codes. The dashboard API table now lists `SystemExit` (status 1) for `serve()` on a busy port; it listed `OSError`, which `serve()` never raises, also in 0.1.2.2. `heavenbase.dashboard.serve` accepts a keyword-only `on_started` callback that receives the dashboard URL once its listener is ready, including when no window opens; `hb dashboard` uses it to print the URL. - **SQLite vector reads.** Computed Core projections evaluate once. Core and typed textual reads distinguish JSON TEXT from packed BLOB with byte-producing text factories on Python 3.10–3.13. This includes precompiled statements and ORM `from_statement()`. They accept UTF-8 with BOM, UTF-16, and UTF-32 from text factories in JSON and packed storage modes. SQLite callback reads and row factories retain the configured text factory's behavior, and SQLAlchemy dialect listeners retain their normal dispatch.

- **Vector scoring.** Portable L2 scoring preserves representable Euclidean distances when squaring a coordinate difference would overflow or underflow. Batched NumPy scoring uses the sum of squares and rescales only rows outside the safe range, so ordinary exact L2 near keeps its earlier speed and agrees with `math.dist` to within 1e-15 relative error. Scan and exact cosine near score a query or stored vector of any finite magnitude by its direction, including one beyond about 1e154, one whose norm exceeds binary64, and one with subnormal coordinates. Exact NumPy scoring takes such a row's dot product and norms from its power-of-two scaled coordinates, as the scan does, so it no longer overflows or loses the digits of a subnormal row. Before, such a row scored 0.0 or NaN in the scan, which was also in 0.1.2.2; the new exact near raised for a large one or ranked a subnormal one wrongly. Ordinary vectors score exactly as before. For large Chroma near results, rescoring returns negative infinity for squared L2 distances beyond binary64 range.

- **Cosine queries of any magnitude.** A native cosine near on a vector store that keeps float32 coordinates (Chroma, LanceDB, Milvus, RediSearch, pgvector, Pinecone, Qdrant, Weaviate, SurrealDB, Neo4j) sends the query scaled by an exact power of two, so a finite query of any magnitude ranks by direction. Before, a query whose coordinates or squares left float32 range could return the wrong rows with NaN, 0.0 or infinite scores, return no rows, or fail in the provider (RediSearch could not pack it; pgvector bound it as infinity). This was also in 0.1.2.2.

- **Known issues** (not fixed in this release; each issue says whether 0.1.2.2 has it, where the question applies):
  - At high drop rates (a drop of a store's database every few tens of milliseconds while other threads keep using the store), LLM cache and Capsule registry calls on that store can stall for as long as the drops continue (64 s in a 60-second run with nine threads). After each drop, the store's next use builds a new workspace under the Context lock, about a second on Python 3.12, and a drop during the build discards it. The Context's other writes waited up to 7.5 s behind those builds. 0.1.2.2 under the same load: calls waited up to 31 s and writes up to 17 s, calls failed with errors, and it served the deleted rows meanwhile.
  - A DuckDB file used through two names in one process, such as a symbolic link and its target, is opened as two databases, and commits made through one of them can be lost, depending on which name is opened first. Use one name per DuckDB file in a process. 0.1.2.2 has this too.
  - An `oracle` engine set to `SERIALIZABLE` fails its own registrations of a `SparseGramIndex` field with ORA-08177; at that level a write whose transaction began before another workspace started indexing the entity is not refused (see **Shared sparse-GRAM index**). Write at `READ COMMITTED` on Oracle while indexes change. 0.1.2.2 had no shared keyword index, so it has no such case.
  - An exception that a signal handler raises during a call (Ctrl-C, an alarm or timeout) leaves neither the Context lock nor a workspace lock held. Only exceptions in such quick succession that the call still handles the first one can leave one of them held: a second one on Python 3.10, and a third one on later versions. Writes of other threads then wait, and `Context.close()` and `reset_default_local_state()` can be refused; build a new Context or restart the process. On Python 3.13 the interpreter itself can skip the exit of a `with` or `finally` when the exception arrives at the end of a pass of a conditional loop, as in 0.1.2.2. An interrupted call of an LLM cache or Capsule registry can leave an entry that a later drop of that database waits for; build a new Context or restart the process after an interrupted call that a drop hangs on. Locks of other libraries, such as SQLAlchemy's connection pool and Python's import lock, can stay held after one exception, as in 0.1.2.2. The reader-writer locks and the hidden-store bookkeeping named here are new in 0.1.2.3.
  - One interrupt can also: during a database drop, leave hidden-store bookkeeping held, so later drops and cache calls wait; during `Context.close()` or a reset, leave the Context marked as shutting down, or open with module services it can no longer use; during a module or entity registration, leave the module resolver's lock held, so a later `close()` hangs (also in 0.1.2.2); and on Python 3.13, rarely, let a writer run beside a reader that had waited while it held a connection. A Ctrl-C that lands in the garbage-collection callback of SQL responses is reported as an ignored exception and lost. Build a new Context or restart the process.
  - After an interrupted call, a drop on the same thread can be refused until the interrupted call's connection is collected; let go of the interrupt's exception, call `gc.collect()` and drop again. The refusal is new in 0.1.2.3.
  - An interrupt that arrives exactly as a transaction block starts to end, or (while the interrupt's exception is kept) right after a row write opened its transaction, can leave that transaction open on its thread; later writes of the thread then join it and may not be committed. Build a new Context or restart the process. 0.1.2.2 could leave the transaction open too, and then refused the thread's later row writes ("Nested Database transactions are not supported").
  - Two Contexts that first open the same new SQLite or DuckDB file at the same moment can get "table already exists" or a catalog conflict; open the workspace again. 0.1.2.2 has this too.
  - A row write joins the transaction that is open on its thread. A `with db.tx()` block that is left on another thread than it was entered on stays open on the first, and a row write of another asyncio task on the same thread joins the block and is rolled back with it. 0.1.2.2 refused such writes. Leave a block on the thread that entered it, and keep row writes of other tasks out of it.
  - A drop of a SQLite database does not wait for connections that use the file, in this or another Context. Calls that overlap it can fail with disk I/O or "malformed" errors, and acknowledged writes can be lost; on Windows the file cannot be removed while it is open. A drop through a symbolic link can leave the target's `-wal` and `-shm` files. Close the file's other users before dropping it. 0.1.2.2 has this too.
  - The check that refuses a wait for a running drop looks only at the thread that holds the awaited lock. A drop can still hang when the thread whose transaction it waits for waits for a Context lock through a third thread, for example on MySQL, where `DROP DATABASE` waits for open transactions. End transactions before calling code that can wait for other Contexts during a drop. In 0.1.2.2 such calls could hang too.
  - On MySQL 8.4, eight processes that each started by upserting 25 new ids of one entity at the same moment met 17 to 39 deadlocks (error 1213) per 200 upserts, against 7 to 19 with 0.1.2.2, and for an entity without a keyword field left 14 to 30 rows without a Catalog row, against 2 to 4: a default upsert commits the entity row before its Catalog row. A mixed workload deadlocked about as often as with 0.1.2.2. Retry error 1213 or use `atomic=True`; `audit()` lists the rows.
  - HeavenBase keeps keyword indexes for MySQL tables of nontransactional engines such as MyISAM too. A failed write there can leave rows and keyword entries out of step.
  - A Chroma collection made under chromadb 0.6.3 or earlier with `hnsw:space=cosine` reports the space `l2` under chromadb 1.5, while its native query ranks by cosine. HeavenBase takes it for an L2 collection, so a near can use the portable scan or report scores of the wrong metric. Make such a collection again with the metric you want. 0.1.2.2 always searched natively.
  - A date or `Decimal` field default cannot be registered on a PostgreSQL main route ("Object of type date is not JSON serializable"), as in 0.1.2.2.
  - A child process forked while another thread is in HeavenBase's one-time initialization can hang on its first use, as in 0.1.2.2. Fork before starting threads, or use the `spawn` start method.
  - The MSSQL backend was not tested against a live server in this release.

# 0.1.2.2 - 2026.08.09

- **MCP**: Migrating to FastMCP 4+ gives HeavenBase native structured tool results and lifespan-owned serving, with no FastMCP 3 compatibility layer. Official MCP `ToolAnnotations` now persist on Tools and round-trip through FastMCP; backend inspection tools project their read-only contract to `readOnlyHint`.

- **Query**: Exact result totals, explicit bounded-result metadata, whole-column statistics, and registered Json reducers replace page-derived aggregation. Caller-authored `code_reduce` remains configurable, while the optional in-process Python extension stays disabled by default.

- **Workspace**: Restored source-backed callables now compare consistently across Contexts, Catalog projection requires complete logical-type compatibility, and vector replicas cannot override authoritative values or nulls during row merging and query hydration.

- **Dashboard**: The OpenAPI-driven interface now uses strict TypeScript under `apps/gui/`, reports result truncation accurately, and preserves cancellable assistant turns through the shared API boundary.

- **Integration hardening**: Workspace MCP serving releases lifecycle locks before entering the blocking server run; external Extension APIs, Skills, Toolkit families, and public tool errors now preserve their owning Context and report collisions safely. CLI output redacts structured secrets, multimodal cache rows digest image payloads and fail soft within a byte budget, and SparseGram defaults are language-neutral and bound to the active SQL dialect.
